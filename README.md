# 小球角斗场 · 斗蛐蛐玩法框架

纯前端、单机、无需后端。**只负责"打"，不负责"操作"** ——
你配好队伍与技能，剩下的交给物理和技能自己跑，胜负由数值与站位决定。

目前的球种（作者原创 IP《反派魔法少女》）：

| 球种 | 定位 |
|---|---|
| **晕彩** | 7 技能 / 远程法术型 |
| **桃夭** | 5 技能 / 近战箭矢型 |
| **缇娜** | 7 技能 / 吸血蝙蝠 + 光柱型 |
| **见晴** | 6 技能 / 三面水镜切换形态 + 起飞 + 精灵变身（魔法少女[白水仙]） |
| **木桩** | 演示用靶子：速度恒为 0、体型大、血量 5000、碰撞伤害 50、无技能 |

> 曾经用来验证框架的几颗"测试球"（空白球 / 技能球 / 蓄能型 / 脆皮型 / 重装型）
> 已按作者要求从**游戏里**删除；它们搬去 `tests/lib/test-balls.mjs` 当诊断夹具

## 怎么运行

ES 模块不能从 `file://` 直接打开（浏览器同源策略会拦截），必须走 HTTP。

**最省事的办法：在资源管理器里双击 `启动器.bat`。**
它会自己起服务器、**等端口真的能应答之后再**打开「本地启动器」页面
（不是写死 3 秒 —— 慢机器上那样会得到一个空白页），
那个页面里就是两个大按钮：**进入游戏** / **素材编辑器**。

```
双击 启动器.bat
   └─ 起服务器（tools/serve.mjs，5173 被占用就顺延 5174/5175…）
      └─ 打开 http://localhost:5173/launcher.html
           ├─ [🎮 进入游戏]        → index.html
           └─ [🎛️ 素材编辑器]      → assets-editor.html
```

**那个黑窗口就是服务器本身，关掉窗口 = 全部停止。**
（`启动预览.bat` 是旧名字，现在只是转发到 `启动器.bat`，老的桌面快捷方式不会作废。）

也可以用命令行，什么都不用记：

```bash
cd game
node tools/serve.mjs
# 它会把三个地址都打印出来（启动器 / 游戏 / 素材编辑器）
```

### 本地启动器（launcher.html）

启动器本身**不是游戏的一部分**，只是一个"进门的地方"，所以它：

| 特点 | 为什么这么做 |
|---|---|
| **不使用 ES 模块** | 万一被直接双击（`file://`），模块脚本会被浏览器拦下 —— 那样连启动器自己都打不开。纯脚本 + 相对样式表在 `file://` 下都能跑 |
| 链接用**同源相对路径** | `serve.mjs` 端口顺延时（5174/5175…）按钮自动跟着走，不用回来改代码 |
| 顶栏**实时报服务器状态** | 「运行中 / 没连上 / 是旧版（缺写回接口） / 没有被服务器托管」四种，并直接写出该怎么办 |
| 内置**打不开怎么办** | 无法访问 / 页面空白 / 编辑器存不上，三条最常见的原因与对应做法 |
| 快捷键 | <kbd>1</kbd> 进游戏、<kbd>2</kbd> 进编辑器、<kbd>R</kbd> 重新检测 |

> 启动器怎么判断"服务器是旧版"：拿一个空请求去打 `POST /__edit`。
> 回 400（`edits 不能为空`）= 接口在，一切正常；回 404 = 跑着的是加这个接口之前的 `serve.mjs`。
> 这条判断和素材编辑器页面里的那条是同一个判据。

### 服务器这一侧单独自检

```bash
node tools/check-server.mjs        # 默认从 5173 起找，也可以 node tools/check-server.mjs 5174
```

只看**真实 HTTP**：三个页面能不能取到、js/css/README 的 MIME 对不对、
404 是不是真的 404、写回接口在不在（空 edits 该回 400）、
不认识的字段有没有被白名单挡下。它**只发只读或必然被拒绝的请求，绝不写文件**，
所以作者正在用编辑器的时候也能随手跑。

和 `check-boot.mjs` 的分工：boot 管"我有没有改坏代码"（不联网），
server 管"服务器这一侧对不对"（只看 HTTP）。"编辑器存不上"十有八九是后者。

同一个服务器还提供**素材编辑器**（可视化调尺寸/透明度/光晕/判定，改完一键写回源码）：

```
http://localhost:5173/assets-editor.html
```

> 写回用的是这个本地服务器的 `POST /__edit`（只认白名单字段、只监听本机）。
> 所以**编辑器必须在 `node tools/serve.mjs` 起的页面里用**；
> 直接双击 `assets-editor.html` 只能看、不能存。

跑测试：

```bash
npm test              # 核心 + 界面（151 + 244 项）
npm run test:core     # 只跑战斗核心（151 项）
npm run test:ui       # 只跑界面渲染（244 项）
```

> 除了这两个套件，`tests/diag/` 下还有一批**诊断脚本**（每个技能逐条对照规格、
> 渲染与音效的录音式验证、长时间对局的卡死扫描）。它们跑得更慢、断言更细，
> 改完引擎或技能后值得跑一遍；完整清单见文末。

### 页面打不开时，先分清是哪一种

这两种情况的表象都是"打不开"，但原因完全不同，处理方式也不同：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 浏览器说**无法访问 / 连接被拒绝** | **服务器没在跑**（最常见：上次的预览窗口被关掉了，或者收藏了旧地址） | 双击 `启动器.bat`（`启动预览.bat` 是旧名字，同样能用），或 `node tools/serve.mjs`，然后访问它打印出来的地址 |
| 页面有内容、但写着**"页面没能启动"**，或整片空白 | 模块加载出错（文件缺失、语法错误、改了代码） | 先跑 `node tools/check-boot.mjs` 看是不是代码问题，再看浏览器控制台的报错 |
| 编辑器**存不上**、报"没有 /__edit 接口" | 服务器是旧版，或者根本没走服务器 | 跑 `node tools/check-server.mjs` 看服务器这一侧；旧版就关掉黑窗口重新双击 `启动器.bat` |

> 分不清是"服务器没开"还是"代码坏了"：`node tools/check-server.mjs` 看服务器，
> `node tools/check-boot.mjs` 看代码 —— 两个都不需要浏览器。

> `tools/check-boot.mjs` 用 linkedom 把**真实的 index.html + js/main.js** 跑一遍
> （还会把素材编辑器页面也开一次、24 个素材逐个点一遍、数值框逐个查空）：
> 入口没抛错、首页内容渲染出来了就算通过。它专门区分"服务器没开"（它自己不受影响）
> 和"代码把页面搞崩了"。改完 `main.js` 或界面模块后可以顺手跑一下，改完素材配置后更要跑。
>
> 顺带一条：`serve.mjs` 在 5173 被占用时会自动顺延到 5174、5175…> 所以**以它自己打印的地址为准**，别死记 5173。

## 已实现的框架
### 运动模型：初始冲量 + 弹性碰撞 + 航向修正

这是本项目的核心物理设定：

1. **开局给每个小球一个方向随机、力道相等的初速**。方向由本局种子决定 ——
   同一颗种子必然得到同一套方向，所以对局依然完全可复现。
2. **小球做匀速直线运动**，速度**大小**始终不变。
3. **改变方向只有三种途径**：
   - **撞到场地边界**：镜面反射，之后额外朝最近的敌人偏转（默认最多 10°）
   - **撞到别的小球**：完全弹性碰撞，沿法线交换速度分量、切向速度不变
   - **持续微转向**（默认 30°/秒）：每帧让航向缓慢朝最近的敌人修正
4. **完全弹性意味着速率严格守恒**：实测四个场地全程速率都是 120.000。

> **为什么需要"航向修正"这一层？**
> 纯弹跳模型下，两个小球很容易长期擦肩而过——尤其在圆形场地，斜反射会让它们
> 进入稳定的周期轨道，实测 1v1 会拖到 130~300 秒还碰不上。
> 而每次撞墙才修正一次太稀疏，所以加了两级修正：
> **撞墙时偏转（最多 10°）+ 每帧微转向（默认 30°/秒）**。
> 两者都只改方向、不改速度大小，因此观感上仍然是"直着走"。
> 实测把平均对局时长从 66.8 秒压到 46.1 秒，接触命中数从 123 提到 204。
> 两者都可以在准备界面里调到 0，退化成纯粹的"只有碰撞才改变方向"。

在准备界面的「开局冲量方向」里可以：
- 选**方向随机**（默认），或用**我来指定方向**逐个拖圆盘设置角度；
- 用批量预设：朝场地中心 / 朝外扩散 / 均匀铺开 / 随机。

在「特殊选项 → 运动参数」里可以调：
初速强度倍率、弹性系数、空气阻力、**撞墙偏转上限**、**持续微转向**。

> 关于"空气阻力"：默认 0（即永不减速）。**调大要谨慎** ——
> 小球减速后挤在一起互相推挤，很容易谁也追不上谁。
> 现在没有僵局兜底机制了，阻力调大可能让对局一直拖到时间上限。
> 建议不超过 0.1，最好保持 0。

### 斗蛐蛐准备

**这一屏在 2026-10 做过一次结构精简**：场地只留几何形状、杂项设置收进「详细设置」，
并新增两条技能规则。

- **队伍数量**：2–6 方（默认 2 方对决，也支持多方大混战）
- **场地**：8 个，**只有几何形状的区别**（形状决定撞墙角度与可走位空间）
  - 方形 / 圆形 / 八角 / 六角 / 三角 / 菱形 / 十边环场
  - 收缩竞技场（十二边形，会向内收缩）—— 它是**唯一保留的"会动"的场地**，
    因为「详细设置 → 特殊选项」里那条「启用场地自带边界收缩」只对它生效；
    把它删掉，那条设置就成了勾了也没反应的死开关。
    引擎侧的区域效果（`zones`）与旋转（`effects.rotationSpeedDeg`）**都还在**，
    以后想加回特殊场地照 `arenas.js` 里的注释补一条数据即可；
    对应的测试改成就地合成场地，机制仍被测到（见 `core.test.mjs` 第 8 节）。
- **场地大小**：按比例缩放整个场地（含区域效果与起始站位），**默认 50%**，范围 30%–150%。
  碰撞频率与场地面积成反比，所以这是控制对局节奏最直接的开关。
- **参与小球**：每队 1–20 个，逐个选择球种，可一键让所有队伍用同一套阵容
- **技能规则**（放在"参与小球"卡片里，因为它直接决定"技能怎么来"）：
  - **无限火力**：解除"每个球最多 3 个"的限制 —— 可以把一个球种的技能全带上
    （晕彩 7 个），也可以一个都不带。互斥组（映霞[荣]/[枯]、公主传承）**仍然生效**，
    那是设计上的"二选一"，不是数量上限。
    关掉它时，已经装了超过 3 个的格子会**自动收回到上限** ——
    否则会出现"界面显示装了 7 个、引擎只认前 3 个"的两边不一致。
    > **实现上的坑（踩过一次，见"开发中踩到的坑"第 37 条）**：
    > `normalizeSkills(speciesId, wanted, maxSkills)` 的第三个参数**不传就是 3**。
    > 界面上有三处会"整理一遍装配"，全都必须把 `skillCap()` 传进去：
    > `equippedOf()`（面板勾选、汇总统计、下一次点击的起点都读它）、
    > `ensureSpecies()`（读存档时整理）、`makeConfig()`（交给引擎那份）。
    > 少传一处的后果不是报错，而是**面板上的勾选被悄悄截断** ——
    > 点第 4 个技能时"存档进了 4 个、面板又显示回 3 个"。
    > smoke 里有一条**逐个勾选**的回归测试专门守这个（见下）。
  - **随机技能**：配置时**不能选技能**，开战前用三格老虎机抽取（见下）。
- **详细设置**（默认**收起**，展开状态记在 `prefs` 里，来回切界面不会折回去）：
  里面是**开局冲量方向** + **特殊选项** + **运动参数**：
  - 由玩家操控其中一个小球（WASD 八向移动 + 鼠标瞄准 + 主动技能按键；
    默认操控蓝色方第一个，按键可自定义 —— 见「玩家操控」一节）
  - 启用场地边界收缩
  - 阵亡后复活（可设等待秒数）
  - 同队伍之间也会互相伤害
  - 比赛时长上限（超时按剩余总血量判定）
  - 显示伤害飘字
  - 运动参数：初速强度倍率 / 弹性系数 / 空气阻力 / 撞墙偏转上限 / 持续微转向
  - 开局冲量方向：方向随机 / 我来指定方向（逐个拖圆盘，或批量预设）

设置会存进浏览器本地存储，下次打开自动恢复。

### 随机技能：开战前的三格老虎机

勾了「随机技能」之后，准备界面**不再让你选技能**（按钮变成"本局随机"且禁用），
开战前先用一段动画把本局抽到的技能依次亮出来，抽完才开打。

- **抽签由引擎做，界面只负责显示**：`core.js` 的 `drawRandomSkills()` 用**本局种子**
  从该球种自己的技能池里抽 3 个（池子小就抽满）。用真随机的话，
  同一条种子重跑会抽到不同的技能 —— 回放、截图复现、诊断全部失效。
- **互斥组在抽的时候就避开**：抽到「公主传承1」就把同组另外两个从候选里剔掉。
  先抽 3 个再让 `resolveLoadout` 整理的话，会出现"老虎机转出 3 个、实际只生效 2 个"。
- **动画**：每颗球一张卡（球名 + 三格转轮），转轮每 70ms 跳一个名字，
  三格依次停下（0.9s / 1.42s / 1.94s），全部停稳后再等 0.8s 才开打，
  也可以点「直接开打」跳过。时间基准用 `requestAnimationFrame` 传来的时间戳
  而不是 `Date.now()`，所以无头测试按固定步长喂帧就能把动画跑完。
- **只给开局就在场的球发牌**：整局是开战前一次算完的，战斗中途召唤的分身
  （晕彩的「析光」）也已经在 `battle.units` 里了 ——
  直接遍历会多出两张卡、显示"还没出生的分身抽到了什么"（实测 1v1 出现了 4 张卡）。
- 抽签结果会写进**战报**（`skillDraw` 事件，第 0 帧那条）：
  动画放完就收起来了，之后想回看"这颗球这局带了什么"只有这里找得到。

### 战斗

- 攻击动画、命中冲击环、伤害飘字、死亡扩散圈、复活提示
- **血条显示在小球上方**，条上给**详细血量数字**（`当前/上限`，条太窄时退化成只显示当前值）；
  **特殊资源条显示在小球下方**（只有带资源的小球才显示，满了会高亮）
- 播放控制：暂停 / 单步前后 / 0.5–8 倍速 / 进度条拖拽 / 跳到最后看结果
- **音效**：控制条上可开关并调音量（程序化合成，无素材；详见"音效"一节）
- 右侧实时态势：每队剩余总血量条与存活数量
- 战报：逐条记录命中、阵亡、复活、结束
- 战后结算：胜方、耗时、结果指纹，以及每个小球的造成伤害 / 承受伤害 / 击杀数

## 架构上的两个关键决定

### 1. 整局一次性算完，界面只推动"播放头"（玩家操控除外）

战斗在开始时就被完整模拟并录成快照序列。因此倍速、暂停、单步、回放全部是免费获得的，
而且**任何倍速下结果都完全一致**。这也是"跳过对局直接看结果"能瞬间完成的原因。

唯一的例外是**玩家操控**：操作没法提前知道，所以那个模式改成**实时逐帧推进**
（照样逐帧录快照，所以打完之后倍速/暂停/拖动进度条回看照旧可用，
只是打到一半时进度条是禁用的）。详见「玩家操控」一节。

> 早期版本试过"实时采样键盘 + 一次性算完整局"：每 6 帧读一次按键状态再模拟。
> 那套在实战里是假的 —— 采样发生在**开战前那次预算**里，
> 玩家在预算的那几十毫秒里根本来不及按键，所以拖屏幕、按 WASD 都不会有反应。
> 现在整段去掉了。

### 2. 定点整数 + 固定时间步 = 结果可复现

所有物理量按 1/1000 为单位存整数，逻辑恒为 60 帧/秒。
「同配置 + 同种子 = 同结果」已被测试覆盖（三次独立模拟指纹逐字节一致）。

这条性质带来三个后续能力：
- 分享一局对战时，别人能复现出**完全相同**的打斗
- 服务端可以重算验证结果（若以后要做排位）
- 调数值时能批量回归，而不是靠手感猜

## 怎么加入一个新角色

1. **放入立绘**：把原画放到 `assets/src/`（用文件名即可，建议纯英文/拼音避免路径问题）。
2. **裁头部贴图**：在 `tools/make-ball-sticker.mjs` 的 `JOBS` 里加一条，填原图路径、
   头部中心与半径（按占图像宽度的比例给，换分辨率不用重算）、压平用的底色，
   然后运行 `node tools/make-ball-sticker.mjs`。
   - 不确定参数时先跑 `node tools/preview-sticker.mjs` 出对比图逐一核对；
     实测最容易错的是**垂直中心**（取成额头位置就会切掉头顶）。
   - 生成后跑 `node tools/check-sticker.mjs` 校验：圆内不透明、圆外透明、
     四角透明、边缘有抗锯齿、左右上下对称。
   - 也可以由作者直接提供裁剪好的图片放到 `assets/characters/`，跳过这一步。
3. **写技能**：在 `js/skills.js` 的 `SKILLS` 注册表里加条目
   （可用的触发方式与引擎原语见该文件顶部注释）。
4. **注册球种**：在 `js/balls.js` 的 `SPECIES` 里加一条，填属性、
   `sticker: { src: 'assets/characters/xxx.png', cx: 0.5, cy: 0.5, r: 0.5 }`
   （贴图本身已是居中正圆，用满即可），以及 `skills: ['技能id', ...]`。
   **只有前 3 个会进默认装配** —— 顺序即优先级（见下一节）。
5. **跑一遍自检**：`node tests/core.test.mjs` 与 `node tests/smoke.test.mjs`。
   加完角色再跑一遍全部诊断（`tests/diag/`）—— smoke 里有几条**通用不变量**
   （默认装配无互斥冲突、技能 id 都能解析）会自动覆盖新角色。

渲染层不需要改动 —— 贴图会按球体半径缩放，并自动加队伍色描边与血条。

### 需要给的东西（照这个填，一次就能做完）

| # | 内容 | 说明 |
|---|---|---|
| 1 | **球种 id + 名字** | id 用纯英文（如 `taoyao`），名字是显示用的中文 |
| 2 | **数值** | 血量 / 移速 / 碰撞伤害。半径默认 16，要不一样再说 |
| 3 | **球体贴图** | 一张（+ 形态切换的第二张，如开华那种） |
| 4 | **技能表** | 每个技能：名字、**触发方式**、关键数值、**官方措辞（逐字）** |
| 5 | **互斥 / 默认装配** | 哪几个互斥、默认带哪 3 个。**不说我就按"前 3 个不冲突"排** |
| 6 | **动画（可选）** | 有没有"射出前的动作"（拉弓那类）？有没有手持物件？ |

> **只有"官方措辞"需要你逐字给**（那一栏是给玩家看的你的原话，我一个字不改）。
> 数值、机制、平衡性检查、以及那套"详细版说明"由我这边补 —— 两套描述共用同一份参数，
> 不会出现"改了数值但说明还是旧的"。
>
> 每加一个新机制，我都会配一条**通用不变量**而不是只测这一个角色 ——
> 比如"默认装配不许有互斥冲突"就是遍历所有球种测的，新角色自动被覆盖。

### 已经能复用的东西（做桃夭时打通的）

| 能力 | 用在哪 | 加新角色要不要重做 |
|---|---|---|
| 球体贴图 / 形态切换 | 晕彩的开华、桃夭的球 | 不用，填路径即可 |
| **手持物件 + 动作状态** | 桃夭的弓（平时 / 拉弓 / 射箭三态） | 不用，填 `bow` 配置即可 |
| **弹道贴图** | 飞行的箭矢 | 不用，发射时给个 `sprite` 参数即可 |
| 前置动作的时间基准 | `castP`（引擎算，写进快照） | 技能声明 `windup` 即可 |
| 瞄准角 | `aimAngle`（朝最近敌人） | 技能声明 `aims: true` 即可 |
| 动作变体 | `castKind`（五连发那种） | 技能实现 `castKind(unit)` 即可 |
| 叠层 / 减速 / 击退 / 回血余数 | 各种 buff | 引擎原语已就绪 |

## 技能装配（默认每个小球最多带 3 个）

魔法少女的技能数量天然很多（设定里每人都有武装 / 奇术 / 开华 / 领域等多套能力），
全带上既没法平衡，也看不出"这一局我想怎么打"的取舍。
所以**装配是开战前的策略选择**：在「斗蛐蛐准备 → 参与小球」里，
每个小球单独挑选要带哪几个技能，**默认上限 3 个**
（想全带上就打开「无限火力」，见"斗蛐蛐准备"一节）。

- **上限**：`js/balls.js` 的 `MAX_SKILLS_PER_UNIT = 3`，改这一个常数即可。
  单次装配还有一个可选参数 `normalizeSkills(speciesId, wanted, maxSkills)` /
  `makeUnitStats(id, skills, { maxSkills })` —— **无限火力就是把它传成 `Infinity`**。
  界面上"能勾几个"和"交给引擎几个"都从同一个 `skillCap()` 取，
  两处各算一次就会出现"界面显示 7 个、引擎只认 3 个"。
- **默认装配**：球种 `skills` 数组的**前 3 个**。
  **顺序即优先级** —— 想让哪几个默认带上，就把它们排在前面。
  **如果前 3 个里有互斥技能，就要把其中一个往后挪**（桃夭就是这么排的，
  见"角色：桃夭 → 映霞两式互斥"）。smoke 里有通用不变量守着这件事。
- **互斥**：技能可以用 `group` 声明"同一组只能选一个"（映霞①②）。
  裁决只在 `skills.js` 的 `resolveLoadout()` 一处，
  引擎 / 存档 / 置灰三边共用同一份口径，不允许各判各的。
  **互斥与数量上限是两回事**：无限火力只解除数量，二选一照旧。
- **随机技能**：勾上之后这一屏不能选，改由引擎在开战时抽（见"随机技能"一节）。
- **换球种**：整格回落到新球种的默认装配（而不是"尽量保留"），行为更可预测。
- **清空是合法的**：一个球可以不带任何技能（等价于普通球）。
- **跨球种过滤**：装配里出现该球种没有的技能会被自动剔除，
  所以改 `SPECIES` 的技能表不会让旧存档读出非法装配。

实现分三层，各管一件事：

| 位置 | 职责 |
|---|---|
| `balls.js` `normalizeSkills()` | 纯函数：去重、过滤、封顶。**唯一的规则来源** |
| `skills.js` `resolveLoadout()` | 纯函数：互斥裁决。**只能选一个的组在这里收敛** |
| `ui-prepare.js` | 存档里的 `loadouts`；技能按钮 + 勾选面板；把装配传给 `makeUnitStats` |
| `core.js` | 只认 `stats.skills`，**不知道装配这回事** —— 引擎不关心技能是从哪来的 |

> `balls.js` **不能** import `skills.js`（会形成循环依赖，`DT` 变成未初始化访问直接报错），
> 所以互斥规则放在 `skills.js`、数量上限放在 `balls.js`，
> 两个纯函数各管一件事，由调用方依次过一遍。

存档格式（`localStorage['ballBattle.prepare.v1']`）新增 `loadouts` 字段：
`loadouts[队伍][第几个球] = ['技能id', ...]`。
**旧存档没有这个字段也能正常读**：会在 `ensureSpecies()` 里按默认装配补齐。

### 测试守着什么

- `tests/core.test.mjs`【5d】：装配规则 + **战斗里真的按装配走**
  （只装射击 → 有射击无蓄力；只装冲刺 → 有蓄力无射击；装配为空 → 一次技能都不发动）。
  最后一条最关键：UI 改对了但引擎没读，就会变成"看着装配了、其实照旧全带"。
- `tests/smoke.test.mjs`【3b】：旧存档兼容、按钮文案、展开面板、勾选生效、
  上限（含"绕过禁用状态也突破不了"）、开战时装配被带进战斗配置。
- `tests/smoke.test.mjs`【7】：**互斥**——同组只留一个、`conflictsWithChosen()`
  与 `resolveLoadout()` 口径一致（界面置灰的必须等于引擎丢弃的）。
  另有两条**通用不变量**（对全部球种生效，以后加角色自动覆盖）：
  默认装配无互斥冲突、把全部技能喂进去也选不出同组两个。

> 球种拥有的技能数量已经不再统一（晕彩 7 个、桃夭 5 个、测试球 2 个），
> 所以上限与互斥两条规则都写成**对所有球种遍历**的通用不变量，
> 而不是针对某个球种写死断言 —— 早先"现成球种都只有 2 个技能"的注释已经过时了。

## 玩家操控（作者 2026-10 的规格）

在准备界面的「特殊选项」里勾上**由我操控其中一个小球**就进入这个模式。
默认操控**蓝色方（0 号队）的第一个小球**（想换就改旁边的下拉框）。

| 规格（作者原话） | 实现 |
|---|---|
| 默认操控蓝色方第一个小球 | `config.playerSlot` 缺省时落到 `units[0]`；引擎记 `battle.playerIdx` |
| 玩家小球开局**不会受到冲量** | 出生时速度直接给 0（别人的随机角照算，所以 `rnd` 序列与结果指纹都不受影响） |
| 被动技能依旧自动触发（裁光、见晴变色…） | 触发方式不是"冷却"的技能原样自动；见晴 ① 虽然内部是冷却触发，但按作者口径标了 `auto: true` |
| 主动攻击技能改为按键触发（魔弹、蝙蝠、映霞[荣]…） | **冷却触发的技能**在玩家手里只认按键（见下） |
| 原间隔改为技能冷却 | 间隔没动，仍是 `trigger.cd`；区别只是"谁来决定何时发动" |
| 弹道初始方向由鼠标位置决定 | 引擎 `aimUnit()`：玩家操控时所有**自己放出的弹道**都朝鼠标（扇形、随机抖动、追踪转速都照旧） |
| WASD 八向移动 | 按住 W+D 就以球速走斜向；松开约 0.13 秒停下（见下） |
| 自定义按键，默认 左键/右键/E/1/2/3 | `prefs.js` 存按键表（按**物理键位码**），准备界面「详细设置 → 技能按键」里改 |

### 哪些技能要用按键

判据只有一条，写在 `skills.js`：

```js
isManualSkill(sk) = sk.trigger.type === 'cooldown' && !sk.auto
```

- **冷却触发** = 原来"每 N 秒自己放一次"的主动技能 → 变成按键发动。
  晕彩【魔弹 / 棱镜 / 析光】、桃夭【映霞[荣] / 映霞[枯] / 春景】、
  缇娜【蝙蝠 / 霰弹 / 三个公主传承】。
- **其余触发方式**（撞墙 / 被动 / 掉血阈值 / 撞击触发）→ 照旧自动：
  裁光、折光、开华、辉光领域、认真拉矢、陀螺、吸血习性、权杖、见晴 ②③④⑤⑥。
- **例外**：见晴 ①「水镜·魔力共鸣（防御）」内部是冷却触发，但作者把它归为
  "变色（被动）" → 标 `auto: true`，玩家不按键它也会自己每 5 秒切色。

按键与技能的顺序一一对应（第 1 键 → 第 1 个主动技能…）。
主动技能超过 6 个时（开着「无限火力」），多出来的**没有默认键** ——
技能栏会写"未绑定"，准备界面可以「＋ 添加按键」补到 12 个。

### 移动手感：直接给速度，但只"逼近"

按住 → 目标是"朝按键方向、大小为球速"的速度，当前速度每帧朝它靠拢，
**约 0.13 秒**（`PLAYER_TURN_SECONDS`）到齐；松开则朝 0 靠拢。
为什么不是"直接把 `vx/vy` 写死"：写死等于每帧都抹掉物理 ——
被撞飞、被击退、撞墙反弹后的新方向都会在下一帧被玩家"瞬间修正"，
看起来就像球在地上滑冰。用"逼近"就保住了那一瞬的惯性，
同时手感仍然跟脚（作者选的就是这一档）。

另外**只对玩家球生效**：AI 球的微转向（`steerDegPerSec`）在玩家球身上被跳过，
否则引擎会一边听玩家的、一边自己往敌人那边拐。

### 鼠标瞄准：只改"初始方向"

`battle.aimUnit(unit, target)` 返回一个单位向量：

- 玩家操控 + 鼠标动过 → **朝鼠标**；
- 否则 → 朝目标（也就是 AI 原来那套）。

所有弹道都走它：魔弹、激光、箭矢（含五连发扇形）、蝙蝠（含随机散开）、
霰弹、棱镜光炮、春景补炮、羽毛。**扇形与抖动都保留** ——
五连发是"整扇转过去"，不是"五支都指向鼠标"。

两个刻意的例外（它们的"方向"存在位置里，不是弹道）：

- **棱镜的光门**：门放在"朝鼠标方向、离敌人那么远"的位置上（门与炮同向）；
- **缇娜的公主传承2（瞬移）**：仍然瞬移到**最近敌人**身边 ——
  它要贴上去撞人/吸附，跟着鼠标飞过去会变成"对着空气突进"。

### 实时推进，但快照照录

战斗界面有两种播放模型：

| 模式 | 怎么推进 | 什么时候能回看 |
|---|---|---|
| 全自动 | 开局一次性算完整局，播放头只是读快照 | 任何时候（倍速/暂停/拖动都免费） |
| **玩家操控** | **按真实时间逐帧 `step()`**（倍速 = 一帧跑多步） | 打完本局之后（整局快照都录下来了） |

所以实时模式打到一半时，进度条 / 单步 / 跳到结果是**禁用**的
（快照还没录完，拖过去只会看到一半的对局）；本局结束后自动解禁，
倍速、暂停、从头重看全都照旧。这也是"边打边操作"与"可回放"两者唯一的代价。

**输入怎么进引擎**：`battle.step(input)` 收一个
`{ dx, dy, aimX, aimY, fire: [技能id…] }`。技能键是**按住即连发**的
（冷却好了就放，没冷却好就等），所以点一下和按住都符合直觉。
`fire` 里装的是**技能 id** 而不是键位：键位映射属于界面，
引擎只认"这一帧要放哪个技能"，两边不会各有一套顺序。

### 界面

- **开战闸门**：进战斗界面**不会立刻开打** —— 画布上先盖一层「斗蛐蛐开始」，
  点下去才真正推进（作者 2026-10 的要求）。两种模式都适用：
  全自动那一局其实**已经在开战前算完了**，只是播放头停在第 0 帧等按钮；
  实时操控则是引擎一步都没走。等待期间的单步 / 拖动进度条 / 跳到结果都是禁用的，
  而且"干等了多久"不会被算进战斗（点开始那一帧会重置计时基准，
  否则一夹到 120ms 就是开局白跑 7 帧）。
- **技能栏**（战场**下方**）：每个主动技能一格 —— 键位 + 技能名 + 冷却倒计时
  （就绪 / 1.3s），下面一行列出"自动触发"的技能名，让玩家知道哪些不用按。
  ⚠ 它一开始是画在 `.stage` 里的绝对定位浮层，结果**盖住了战场下沿那条带** ——
  球和弹道跑到下面去就"看不见了"。现在它是画布下方独立的一行。
- **鼠标准星**：一条从自己球心指向鼠标的虚线 + 准星，免得"打了半天不知道朝哪"。
- **准备界面**：勾上"由我操控"后出现**选择小球**与**技能按键**两块，
  按键表会把"这个键 → 哪个技能"直接写出来（与引擎同一份 `manualSkillIds`）。

### 输入三条容易踩的线（都已经写进诊断）

| 线 | 为什么会踩 |
|---|---|
| **按下的动作要锁存** | 输入是"每帧现读一次按住状态"。一次很快的点按如果**按下与松开都落在同一帧的间隙里**，那一发就整发丢掉 —— 表现是"有时候点了没反应/特效没了"。所以维护两个集合：`keysDown`（按住）+ `keysEdge`（自上次喂给引擎以来按下过），技能键取两者之并，喂完就清边沿 |
| **贴脸开枪也得看得见** | 贴着墙（或贴着敌人）开火时，弹道**在出生那一帧**就撞上东西 → `alive = false`，而快照是帧末才记的，于是这一发**一帧都没被画出来**：点了左键，屏幕上什么都没发生。引擎侧现在有一条"最短可见时间"（`PROJ_MIN_VISIBLE_FRAMES = 5`）：出生头几帧不许直接消失，改成**冻在原地、把剩下的时间当寿命用来淡出**（冻住期间不再移动、也不再判命中/撞墙，所以不会重复结算伤害、也不会多冒几次水花）。自动模式几乎见不到这个现象 —— AI 总是朝敌人打，所以它基本是"手操专属"的 |
| **贴图要在"画到它之前"开始加载** | 全自动模式是"整局算完 → 预热所有弹道贴图 → 再播"，所以贴图早就绪。实时操控在开战那一刻调 `preloadProjSprites` 时**一枚弹都还没有**，调色板是空的 —— 于是那种弹道要等第一次绘制才现加载，头一两帧只能画程序化光点（看着像特效没了）。现在每帧补一次：调色板/单位数一变就再预热 |
| **播放头到末尾 ≠ 打完了** | 实时模式下播放头每帧都等于总帧数，拿它当结束判定会开局自己按暂停（见坑 59） |

### 右键与鼠标手势：别让一局被"手势"带走

右键是 2 号技能键，而**按住右键拖动**在不少浏览器 / 鼠标驱动里是"后退手势" ——
一触发浏览器就退回上一个路由，这一局当场没了。两道防线：

1. **整个战斗界面屏蔽右键菜单与中键**（`contextmenu` / `auxclick`）。
   以前只挡了画布：在顶栏、侧栏、播放条上按右键照样弹菜单。
2. **给路由挂一个"守门人"**（`window.__battleScreen`，由战斗界面注册）：
   对局**还在进行**时，非本界面主动发起的跳转会被拦下 ——
   地址改回 `#/battle`、界面原样留着，并在界面上给一句提示。
   - "还在进行"两种模式的定义不同：实时操控看引擎（`battle.over`）；
     全自动模式**开局就已经算完了**，所以要看播放头有没有播到头
     （拿 `battle.over` 当判据会让守门人在全自动模式下等于没挂 —— check-boot 抓到的）；
   - **连按两次后退（1.5 秒内）就放行** —— 想退出的人不会被硬关在里面；
   - 自己点「重新准备 / 换种子重开」当然畅通（先置一个 `leaveRequested`）；
   - 换界面时 `main.js` 会调守门人的 `detach()`，把键盘/鼠标监听一并摘掉 ——
     否则回到准备界面后那些监听还会继续吞键盘事件。


### 已知取舍

- **触屏拖动操控已移除**：旧的那套是配合"开局一次性算完整局"写的
  （拖动只改一个键盘状态集合，而那个集合只在预算阶段被读取，实战里其实不生效）；
  现在鼠标要用来瞄准、左右键还是技能键，再按住拖动就会和开火打架。
- **回看的是快照**：拖动进度条时渲染层读的是历史快照，
  但个别"外观字段"（例如长剑长度）是从引擎当前状态现读的 ——
  这在**借来的技能**上会有细微不一致（借来/归还的瞬间），不影响判定。
- 玩家球的"朝向"（`face`）仍由移动方向决定：站着不动时见晴 ② 的长剑会保持
  上一次的挥砍方向，而不是转向鼠标（作者没有要求改这一条）。

### 辉光领域的画面（领域展开）

作者提供的**一张横向长图**（3360×1440）作为领域背景 —— 见 `js/balls.js` 里晕彩的
`domain` 配置。整段效果分两小节，**参数全在配置里，改数值不用动渲染代码**。

| 阶段 | 表现 |
|---|---|
| ① 展开 | 一圈**气浪**从**激活时晕彩所在的位置**向外扩散；气浪扫到哪里，领域才在哪里浮现（实现是两次裁剪求交：场地形状 ∩ 气浪圆） |
| ② 展开后 | 背景**缓慢向右滚动**，整体不透明度稳定在 `opacity`（默认 **42%**，作者要的 30%~50%） |

| 字段 | 含义 |
|---|---|
| `revealSeconds` | 气浪从中心铺满全场的时间（1.3 秒） |
| `opacity` | 展开完成后稳定下来的不透明度 |
| `fadeInPortion` | 前 25% 的展开过程里淡入，避免"啪"地冒出来 |
| `scrollUnitsPerSec` | 展开后向右滚动的速度（世界单位/秒） |
| `ringWidth` / `ringAlpha` / `glow` / `core` | 气浪环的宽度、亮度与配色 |

**几个刻意的决定：**

- **气浪中心是固定的**（激活那一刻晕彩的位置），不跟着她跑。跟着跑的话，
  离她远的那半边永远扫不到，"铺满全场"就不成立。引擎只在激活时记一次
  （`battle.auroraAt` / `auroraCenter` / `auroraStyle`）——
  静态量不需要每帧进快照，和 `battle.aurora` 这个布尔量同理。
- **时间全部由 `snap.f` 推出来**，所以暂停会冻在那一帧、拖进度条会跟着倒回去。
- **滚动用镜像平铺**：图片按"正-反-正-反"首尾相接铺开，横向移动时接缝两边
  本来就是同一条边，所以永远看不到跳变。直接平移一张不循环的图，
  走到边界会"啪"地跳回去（这张图一次滚完要 293 秒，跳一次大概正好在关键时刻）。
- **按场地高度等比缩放**，横向必然溢出（图是 7:3）—— 溢出的那部分正好拿来滚动。
  竖直方向刚好铺满，**绝不拉伸**。
- **领域层裁到场地形状**，不是外接矩形。只按矩形裁的话，圆形/多边形场地外面
  也会糊上一层极光，看起来像画到画布外面去了。

> **这一版把原来的程序化极光条换掉了。** 之前 `_aurora()` 是用 7 条半透明色带
> 画出来的占位效果；作者给了正式背景图之后它就被这张图取代了。
> 想让它作为叠加层保留，说一声。

### 映霞两式互斥（`group: 'yingxia'`）

①②是同一个技能的两个形态，**只能选一个**。互斥不是写在界面里的，
而是在 `js/skills.js` 里给两个技能打同一个 `group` 标记，然后由
`resolveLoadout()` 统一裁决。三个地方共用这一份裁决，缺一个就会出现
**"界面显示装了 2 个、引擎只认 1 个"**：

| 位置 | 用途 |
|---|---|
| `core.js` 建单位时 | 权威口径 —— 引擎真正认哪几个 |
| `ui-prepare.js` 存装配时 | 玩家勾选后落盘的口径 |
| `ui-prepare.js` 渲染勾选框时 | 把互斥项**置灰**并写明原因（`conflictsWithChosen()`） |

> **默认装配的排序是有意的**：`balls.js` 里桃夭的技能表是
> `[荣, 认真拉矢, 春景, 枯, 陀螺]` —— 故意把「枯」排到第 4 位。
> 因为默认装配取的是**前 3 个**，如果照①②③④⑤的顺序写，
> 默认装出来的桃夭就会自带一对互斥技能（看起来装了 3 个，实际只生效 2 个）。
> smoke 里有一条通用不变量守着这件事：**每个球种的默认装配都不允许有互斥冲突**，
> 以后加新角色时会自动被拦下。

### 「真正的打击」是怎么定义的

陀螺的"被攻击"**只算真正的打击**：近战碰撞、弹道命中、爆炸。
**不算**的两种：

| 不算的情况 | 为什么 |
|---|---|
| 裁光质点 / 细线的每帧接触伤害 | 一秒 60 次接触，会瞬间把层数顶满 |
| 场地灼烧等持续区域伤害 | 同上，而且玩家没有躲避的余地 |

实现上是靠 `_damage()` 里算出的 `heavy` 标记（`!opts.quiet && kind !== 'zone'`），
技能侧只写一行 `if (!ctx.heavy) return;`。
**这条规则和"每帧伤害"机制是同一条边界的两面**（见第 28、45 条踩坑）。

### 「认真拉矢」的两条边界

1. **没装这个技能就不该叠层**。叠层逻辑挂在箭矢的 `onHit` 上，
   而箭矢不管装没装「认真拉矢」都会发射 —— 所以每个入口都要
   `hasAim(unit)` 查一次。漏查的后果是：不带这个技能的桃夭
   照样在偷偷叠层，满层时箭矢打出了 80 而不是 50。
2. **春景的光炮不吃这个加成，命中了也不叠层**。光炮是 `tag: 'chunjing_cannon'`
   的另一套体系，和 `tag: 'arrow'` 的箭矢在代码里就是两条路径。

### 为了桃夭新增的引擎机制

| 机制 | 说明 |
|---|---|
| **击退 knockback** | 弹道命中时给目标一个冲量。走的是"改速度"而不是"改位置"，所以和弹性碰撞、边界反弹都不打架。**桃夭的技能目前都没用它**（映霞[荣]的击退已按作者要求去掉），保留是因为测试球的冲刺还在用 |
| **减速 speedSlow** | 走统一的速度模型（基础 + 加成 − 减益），所以陀螺的加速、枯的减速、开华的提速是**叠加**而不是互相覆盖；带帧数上限，到期自动撤销 |
| **回血余数累积** | 回血量常是"每秒 10 点"这种除不尽 60 的数（每帧 1/6 点），`_heal()` 用 `healAcc` 把余数攒起来，不会因为每帧不足 1 点而一点都回不上 |
| **旋转角进快照** | 陀螺的转速是观感的一部分，旋转角写进快照（下标 12），暂停/回放才对得上 |
| **碰撞伤害的动态加成** | 每层 +2 碰撞伤害，靠 `spinMeleeBonus` + `refreshMelee()` 重算，而不是直接改 `melee` —— 否则层数涨上去就再也降不回来 |

### ④ 的空中口径：减半、照常放技能、每秒最多转 45°

作者 2026-10 把"免疫"整条口径换掉了，现在空中是"半肉 + 全功能"：

| | 规则 |
|---|---|
| 受伤 | **所有伤害减半**（`dmgTakeMul = 0.5`，走 `_damage` 出口，弹道 / 碰撞 / 光柱 / 帧伤全覆盖）。不再是"免疫"，也就**不再发 `immune` 事件** |
| 技能 | **①②③⑤⑥ 全部照常**：空中照样挥长剑、照样借魔弹/激光、① 的回血与护盾照常涨。起飞**不再**设 `invulnFrames` / `noAttackFrames` |
| 追踪 | 移动中**每秒最多修正 45°** 朝最近的敌人（这是**航向**，速率不变） |
| 撞墙 | 撞到墙**立刻**把航向精确对准最近的敌人（`wallHoming`，瞬间完成、不受 45°/秒 限制）—— 否则 4 秒滞空就是随机乱撞 |

**45°/秒 为什么要在引擎里做**：一帧里能改航向的地方不止一处 —— 引擎的全局微转向
（详细设置里的「持续微转向」，默认 30°/秒）会**先**转，技能自己的追踪在 `onMove` 里
**再**转，两者叠加实测 75°/秒，那就不是"最多 45°"了。所以新增了
`turnCapDegPerSec`：单位登记上限后，引擎在 `onMove` 之后、积分之前把本帧航向
钳在"本帧开始航向 ± N×DT 度"之内 —— 不管有几个来源，**总量**都守在上限以内。
（在详细设置里把微转向调到 60°/秒也仍然是 45°/秒，诊断里专门钉了这一条。）

### ④ 的成长：每飞完一次，永久变强

作者 2026-10 的新机制：「见晴每次起飞过后，速度永久加 5，下次起飞的帧伤增加 0.5，可叠加」。

| | 规则 |
|---|---|
| 结算时机 | **落地那一刻**（所以第 1 次飞行用的还是原始数值，第 2 次起才吃到 +0.5） |
| 移速 | 每次 **+5**，**永久**（和空中那份临时的 +150 分开记：落地只撤 +150） |
| 帧伤 | 之后每次飞行的帧伤 **+0.5**，可叠加：第 1 次 5、第 2 次 5.5、第 3 次 6… |
| 事件 | 每次成长发一个 `flyUpgrade`（带当前帧伤），画面上一圈金色光环 + 三道上升线 |

**0.5 是怎么落地的**：伤害与 HP 都是整数，`_scaledDamage` 会先 `round` 一次
（5.5 → 6，叠几层就整体偏掉）。所以这里用**余数累积**（和"每秒回 15 血"同一套）：
攒够 1 点才真的结算一次，表现上是 5、6 交替，长期平均严格等于 5.5/帧。
与 ⑤ 的伤害倍率是**叠乘**的（5.5 × 0.7 = 3.85/帧）。

### 为见晴新增的引擎能力

| 能力 | 做法 | 为什么这么做 |
|---|---|---|
| **护盾** | 用物种的「特殊资源」条当护盾池（上限 300），吸收写在技能的 `onBeforeDamage` 里 | 资源条本来就会画在血条下方 —— 护盾看得见，才谈得上"要不要装 ①"。吸收走引擎留给"护盾/减伤"的官方出口，不新开机制 |
| **伤害可以完全挡下** | `onBeforeDamage` **显式**返回 `{amount: 0}` 时，这次伤害整个取消（不再夹到 1 点）；没返回 amount 的钩子照旧至少 1 点 | 护盾正好够用的那一帧必须是"一点血都不掉"。以前 `Math.max(1, …)` 会让护盾永远漏 1 点 |
| **撞墙锁定 `wallHoming`** | 撞墙反射之后，把航向**精确**指向最近的敌对小球（`_aimAtNearestEnemy`），速率严格不变 | 见晴起飞时"只与墙壁碰撞"，若撞完只是随机反弹，5 秒滞空就白飞了。默认那套"最多偏转 10°"对地面单位是防僵局，对空中单位不够用 |
| **限速转向 `turnCapDegPerSec`** | 单位登记一个上限（度/秒）。引擎在 `onMove` **之后**、积分之前，把本帧航向钳在"本帧开始航向 ± 上限×DT"之内 | 一帧里改航向的来源不止一处（引擎微转向 + 技能追踪），**叠加**着算就超了：实测 30 + 45 = 75°/秒，而作者要的是"最多 45°"。把上限交给引擎统一裁决，技能只管"想往哪转"。撞墙锁定不受限（本来就是瞬间的） |
| **减伤 `dmgTakeMul` / `dmgTakeMulFrames`** | `_damage` 里乘一次（帧伤也乘），到点由**引擎**还原成 1 | ④ 从"免疫"改成"所有伤害减半"后，需要一个"按倍率挨打、且能自动到期"的出口。倍率放在"是否命中/闪避/护盾"之前，所以减半与护盾吸收、闪避都按同一次结算顺序走 |
| **无敌 `invulnFrames`** | `_damage` 开头判：免疫一切，但**帧伤放行**（`opts.frame`） | 作者确认"buff 类伤害 = 被命中后持续掉血的伤害"，所以裁光细线那类每帧伤害照样打得中她。⚠ ④ 已经**不再**用它（改成减半），这条是引擎保留能力，目前只有诊断在用 |
| **穿透 `phasingFrames`** | `overlapping()` 里判一次，**外加 `_attackPair` 开头一道守卫** | 碰撞冲量、位置分离、撞伤**三个地方都先问它**。⚠ `_resolveAttacks()` 有**自己的网格**、不走 `overlapping` —— 只改 `overlapping` 会漏掉碰撞伤害（实测：飞过去时除了 5/帧，还每 0.5 秒多挨一下 30 点的碰撞伤害，见第 55 条） |
| **禁止攻击 `noAttackFrames`** | 引擎跳过"冷却类技能 + onThink"，其余钩子照常 | 作者的原话是"不会发动其他技能的攻击（技能①中的防御效果依然可以触发）"—— 攻击与 buff 在引擎里本来就是两条路径（冷却分发 vs 被动/hooks）。⚠ ④ 现在**不再**用它了（"空中可以正常用其它所有技能"），保留为通用能力 |
| **限时的移速倍率 `speedMulFrames`** | 到点由**引擎**还原成 1 | 不能让"施加减益的人"负责收尾：她可能已经阵亡，目标会被永久打对折（吸附那个坑就是这么来的） |
| **减伤在出口处统一扣** | ⑥ 羽毛把 `meleePenalty` / `skillPenalty` 写在**目标**身上，`_damage` 结算时按 `kind` 扣，帧伤跳过 | 伤害出口只有这一个，一处覆盖碰撞 / 弹道 / 光柱 / 爆炸所有来源，不会漏；也保证"帧伤不减"这条口径只有一个地方实现 |
| **快照 + 3 位** | 16 防守水镜色 / 17 借用水镜色 / 18 状态位（bit0 飞行中） | 随机切色与滞空都是"每帧状态"，渲染层不能自己猜、更不能读引擎实时字段（回放会画错） |

| ③ | 魔力霰弹 | 冷却 2 秒 | 一轮 3 发在 0.5 秒内打完，每发随机偏 0~15°，每发 30 伤害 |
| ④ | 权杖 | 被动 | 碰撞 +15（**不影响吸血习性的 30**）；霰弹 / 蝙蝠伤害 ×4/3（30→40、6→8）；追踪偏转 +30° |
| ⑤ | 公主传承1 | 冷却 10 秒 | 3 秒时间停止：除缇娜外的球**不能移动、不能开火、冷却也停**，但持续伤害照跳 |
| ⑥ | 公主传承2 | 冷却 10 秒 | 立刻放一只蝙蝠（不带蝙蝠技能也放）+ 瞬移到目标边上撞击；带吸血习性则直接吸附 |
| ⑦ | 公主传承3 | 冷却 10 秒 | 蓄力 1 秒后从身上射出锚定光柱，直径 32（= 球直径），随目标转向；持续 2 秒、每秒 3 次判定、每次 35（共 6 × 35 = 210） |

> **⑤⑥⑦ 互斥**（`group: 'princess'`），三个只能选一个 —— 它们都是"每 10 秒一次"的大招，
> 全装就会在 10 秒那一瞬一起发动。

### ② 偷学：放一次，还是借 N 秒？（作者 2026-10 报的 bug）

作者发现：「缇娜通过蝙蝠发动见晴的变色能力时，并没有触发对应效果」。

原因很干脆：**那类能力的 `run()` 只切一次颜色**，真正的效果全在它自己的
被动 + 每帧钩子里（淡绿每秒回血、淡粉每秒涨护盾、长剑每帧找目标挥砍）。
缇娜身上没有那些钩子，于是"发动了"——画面上甚至真的换了一圈颜色（颜色位在
`ringKind` 里，快照照抄）——但一滴血都没回、一点护盾都没涨。

修法按作者的口径分四种：

| 偷到的技能 | 处理 | 例子 |
|---|---|---|
| **一次性**（一次 `run()` 就是完整效果） | 照旧：立刻放一次 | 晕彩的魔弹 / 光门 / 分身、桃夭的箭矢 / 光炮、缇娜自己的霰弹 / 时停 |
| **持续发动型**（技能标了 `sustain: true`） | 把这个技能**临时装到缇娜身上 5 秒**：被动、每帧钩子、冷却触发全都真的跑起来，到点自动归还 | 见晴 ①（变色 + 回血/护盾/碰撞加成）、②（常驻长剑）、③（变色 + 借来的魔弹/激光）、⑤（精灵变身 —— 借来会变成"小体型 + 伤害 ×0.7"，对缇娜其实是削弱） |
| **④ 起飞**（持续型里的特例） | 借来的那一刻**立刻起飞**，滞空用它自己的 **4 秒**（不用走满 1560）；落地那份"每次飞完永久 +5 移速"照给，**归还时不会被撤掉**（作者："获得叠加移速"） | 见晴 ④ |
| **⑥ 我很可爱** | **立刻发一根羽毛**（不用等掉血）—— 它是"放一次"那一类，只是给 ⑥ 补了一个 `run()` | 见晴 ⑥ |

几个实现上的要点：

- **装载与本体技能共用一条路**（`_attachSkill`）：跑 `passive` → 登记 hooks。
  否则"偷来的"和"本体的"会走出两套行为，这类偏差极难查。
- **分发要看得见借来的技能**：`_skillIdsOf(unit)` = 本体 + 借来的。
  见晴 ① 是"每 5 秒切一次色"的冷却技能 —— 它的 `run()` 只在分发里跑。
- **到期由引擎摘钩子**（`revokeSkill`），再调技能自己的 `onUnborrow` 收尾。
  不能让"借出方"（见晴）负责收尾：她可能已经阵亡了 ——
  这和"限时移速倍率必须由引擎还原"是同一个道理。
- **钩子按函数引用一个个摘**，不能整个清空 `unit.hooks`：缇娜自己也有钩子。
- **重复借只续时长，不重跑被动**（否则移速 +10 会叠成 +20）。
- **要"原样还回去"就得在被动之前记账**：⑤ 的被动会真改单位的体型与伤害倍率，
  所以引擎额外给了一个 `prepareBorrow`（在 `_attachSkill` **之前**调用）——
  技能在那里先把旧值存一份，归还时照着还原。光靠"除以倍率"反算会有取整误差。
- **资源条要临时换掉**：见晴 ① 的护盾池用的是"特殊资源"条，而缇娜身上那条是
  **魔力（上限 5）**。不换的话，护盾会写进魔力计数器 —— 当场把
  "魔力满 5 → 再偷一次"的循环点着。所以借用期间换成水镜护盾（上限 300），
  归还原样还回去。副作用只有一条：这 5 秒里蝙蝠返回给的魔力会加成到护盾上
  （同一根资源条），归还时护盾清零、魔力回到借用前的值 —— 相当于那几点
  魔力换成了护盾，不是凭空丢掉。

编辑器里可以改这个秒数：**缇娜 · 技能数值 → 蝙蝠 · 偷到持续型能力时借多久**。

### 为了缇娜新增的引擎机制

这个角色一次引入了六套系统。它们都是**通用**的，不是缇娜专属的写法：

| 机制 | 说明 |
|---|---|
| **吸附 latch** | 把一颗球按在另一颗身上。位置强制贴到"刚好接触"，目标身上挂减速 + 沉默、吸附者挂近战免疫。生命周期由设置它的技能收尾（见第 49 条） |
| **沉默 silencedFrames** | 挡技能分发，**但撞墙触发的不挡**（作者原文"除碰撞墙体使用的技能以外"） |
| **技能冷却 skillCd** | 引擎在分发技能前统一检查它。所以"技能之间的硬性间隔"不需要技能自己判断 —— 写到 skillCd 里就是硬性的（缇娜的吸附间隔就是这么做的，而且是从**吸附结束**起算，不是从吸附开始） |
| **近战免疫 meleeImmuneFrames** | 与隐身的免疫合并到同一个判定点，但来源分开记（"看不见所以打不到"和"被缠住所以打不到"是两回事） |
| **移速乘子 speedMul** | "降低一半"是**对折**而不是减 20。先加减、再乘 —— 否则陀螺的加速度会按原样加回来 |
| **追踪 homing** | 每秒最多转 N 度（**转速上限**，不是总偏角上限）。打不到就会绕圈追 |
| **转向上限 turnCapDegPerSec** | 单位级：一帧内**所有**转向来源合计不得超过它（引擎在 `onMove` 之后统一钳）。与"持续微转向"那个全局设置无关，是"这一帧最多转这么多"的最终裁决 —— 见晴 ④ 的 45°/秒 用的就是它 |
| **返程 returnTo** | 命中后不掉头消失，而是朝主人飞回来，抵达触发 `onReturn` |
| **锚定光柱 anchor + tickDamage** | 位置每帧从主人身上抄、方向朝锁定目标；伤害按节拍在"与光柱同宽同长的胶囊"里结算。长度 `beamLen` **判定与绘制共用一个数** |
| **时间停止 startTimeStop** | 只落在三处：冷却递减、位移积分、技能分发。区域伤害与场地物件的每帧结算**不在这三处**，所以天然"照常跳" |
| **褪色** | 快照对象上带一个"豁免者下标"（`snap.ts`），渲染层据此把别的球画成灰度。战场级状态存一份，不抄到每个单位身上 |
| **借来的技能 `borrow`** | `grantSkill(unit, id, 秒)` / `revokeSkill(unit, id)`：临时把一个技能装到单位身上（和本体技能走同一套装载），到期由引擎摘钩子并调技能自己的 `onUnborrow`。用途见上一节「② 偷学」 |

### ⚠ 一个建议你调的数：蝙蝠的转弯半径

作者给的偏转是"每秒最多 60°"。这个数本身看不出强弱，要换算成**转弯半径**：

```
半径 = 速度 ÷ 角速度
```

原来速度 260 时半径约 **248 世界单位** —— 场地只有约 700×500，
蝙蝠**掉一次头要画一个半径 248 的圆**，于是它基本直飞、只在末端划一道弧，
稍微移动的目标就追不上（观感就是"蝙蝠不追踪"）。
**速度降到 150 之后半径约 143，权杖加成到 90°/秒后约 95** —— 这才追得住人。

诊断里有一条断言把半径算出来直接钉住（`蝙蝠的转弯半径在场地尺度内`），
并同时报出装权杖后的值。**以后调速度或偏转角，这一条会立刻告诉你半径变成了多少**，
不用自己脑算。

## 动作动画：射出前的姿势（手持物件 / 拉弓 / 五连发）

技能的**前置动作**（拉弓、蓄势、举盾）和技能效果本身是两件事。
这一节记的是这套机制的实现方式，以及**给作者的关键帧约定**。

以桃夭的映霞为例：箭是"到点射出"的，但弓在**射出之前**就要开始拉。
这带来一个渲染层解决不了的问题：

> **渲染层只读快照，它看不到技能冷却还剩多久** ——
> 所以它无从知道"还有 0.4 秒就要射箭了"。
> 若让它按 `performance.now()` 自己推算，**一按暂停弓就一直拉着不放**。

所以施法进度必须由引擎算、写进快照。快照因此从 13 位扩到 15 位：

| 位 | 字段 | 说明 |
|---|---|---|
| 13 | `castP` | 施法进度 0~1，**射出那一帧恰好 = 1** |
| 14 | `aimAngle` | 瞄准角（角度制），朝**最近的敌人** |
| 15 | `castKind` | 该用哪套美术（也是施法**变体**）：0 普通 / 1 五连发 / 2 映霞[枯] |

> **`castKind` 的含义是"这个单位现在该用哪套弓"，不是"这一发是什么变体"。**
> 所以**没在拉弓时也不能归 0** —— 0 在美术表里是「映霞[荣]」，
> 归 0 会让只装「映霞[枯]」的桃夭平时举着荣那把粉弓，只有拉弓那 2 秒才变回花枝弓。
> 引擎在"没在拉弓"时照样问一遍技能的 `castKind()`（见 `idleCastKind()`），
> 构造函数记的第一帧也补上（实测恰好是第 1 帧闪了一下粉弓）。
> `bow.mjs` 里有一条断言逐帧看"枯那一局整局都指向枯那一套"。

> **为什么还要一个"变体"字段**：五连发和单发的**拉弓动作时长完全一样**，
> 光看 `castP` 分不出来。但作者要求"五连发时在 2 的基础上，于同一个搭箭节点
> 扇形多排四根箭" —— 画面上确实要多画四根箭，所以必须由引擎额外告诉渲染层。
> 技能可以声明一个可选的 `castKind(unit)`，引擎取"进度最大的那个技能"的变体，
> 保证进度和变体来自同一个技能。

技能侧只要声明两个字段，引擎就会开始维护它们：

```js
aims: true,      // 这个技能朝最近的敌人出手 → 每帧算瞄准角
windup: 0.4,     // 射出前的动作时长（秒）→ 据此算 castP
```

`castP` 的算法是 `(windup − 冷却剩余) / windup`，在"冷却递减之后、技能发动之前"计算。
这个位置很关键：冷却归零那一帧 `castP` 已经是 1，**与弹道生成同帧** ——
动作和箭不会差半个身位。

> **`aimAngle` 不能复用 `face`。** `face` 是"当前运动方向"（由速度决定），
> 而瞄准是"朝最近的敌人"。小球一边匀速飞一边瞄，这两个方向经常差 90° 以上
> （诊断实测 600 帧里有 466 帧不同）。

### 手持物件为什么必须和球体分开画

弓不是画在球体贴图里的，而是走**独立的一条绘制路径**（`render.js` 的 `_bow()`）。
三个约束在这一步同时解开：

1. **球体贴图会被 `ctx.clip()` 裁成圆形。** 弓画在球外面，跟着球体贴图走就会被整条裁掉。
   独立绘制路径不 clip，弓才出得来。
2. **球装陀螺时会自转。** 自转是靠 `ctx.rotate(spin)` 转整个贴图的。
   弓若在同一个变换里，就会一边瞄准一边翻滚 —— 一把"瞄着敌人的弓"跟着球打转，看着就是坏的。
   独立绘制之后弓**天然不继承自转**，这个冲突自动消失（诊断里有一条专门验证：
   弓的 drawImage 必须排在自转的 rotate 之前）。
3. **两者朝向的来源本来就不同**：弓朝敌人（`aimAngle`），球贴图自转（`spinAngle`）。

绘制顺序是**先弓后球**，让球盖住弓的中间，看起来像"球握着弓"。

> 没装「映霞」的桃夭**不拿弓**（一个只带春景/陀螺的桃夭不该举着一张弓）。
> 这一条在引擎的 `_initUnitSkills` 里判：没装瞄准类技能就把 `u.bow` 置空。
> 引擎是权威口径，渲染层只读结论。

### 动作状态：平时 / 拉弓 / 射箭

作者给的是两张弓图，对应三个时刻（`js/balls.js` 的 `bow` 配置）：

| castP | 状态 | 画面 | 图 |
|---|---|---|---|
| `= 0` | `idle` | 平时：弓举着，弦是直的 | `taoyao_bow_idle.png` |
| `0 < castP < 1` | `draw` | 准备射箭：弦拉开，**搭好一支箭** | `taoyao_bow_draw.png` |
| `= 1` | `shot` | 射箭那一帧：弓复位、箭已离弦 | 同 `idle`（`shot` 留 `null`） |

`shot` 只持续**一帧**（16ms）—— 这是刻意的"撒放"效果，弓啪地弹回去。
作者原话是"射箭的时候切换为 1"，所以 `shot` 直接复用 idle 那张图；
以后要单独画一张撒放帧，往 `bow.shot` 里填路径即可，**代码不用改**。

### 五连发：同一个搭箭节点上的扇形

作者原话：「当同时射出五根箭矢的时候，在 2 的基础上，在同样的搭箭节点扇形额外排布四根箭矢。」

`draw` 那张图里已经搭着一支箭，所以五连发时**额外再排 4 根**就是 5 根：
每根都以**同一个箭尾**（`bow.nock`）为轴扇形分布。
这些箭是"武器的一部分"，所以写在**弓的局部坐标系**里 —— 跟着弓一起转，
也就不受陀螺自转影响。

> **扇形角度必须等于箭真正飞出去的角度。** 画这个扇形的全部意义就是
> "预告这五发往哪飞"，所以渲染层用的是和技能**同一个公式**：
> `(k/(n−1)×2 − 1) × 张角的一半`，再把正中那一根跳掉（0° 那根已经画在 `draw` 图里）。
>
> 这一条是**收尾时才发现的问题**：原先渲染层自己写了一套"4 根均匀铺在 ±18° 内"
> （实际落在 ±3.6° / ±10.8°），而箭真正飞的是 0° / ±12.03° / ±24.06° ——
> **张角差了一倍多**，画出来的扇形根本没有预告作用。
> 现在两边的数由一条断言钉在一起（`弓 5 发 ±24.06° vs 技能 5 发 ±24.06°`），
> 改一边不改另一边会立刻变红。

### 两式弓 = 多套美术 + 一张 `kindArt` 查表

桃夭有两个互斥技能（映霞[荣] / 映霞[枯]），两把弓长得完全不一样
（粉弓 vs 墨色花枝弓）。而弓的美术挂在**球种**上，渲染层从球身上看不出
当前放的是哪一式 —— 所以配置写成"多套美术 + 一张查表"：

```js
bow: {
  kindArt: [0, 0, 1],        // castKind(0 普通 / 1 五连发 / 2 枯) → 第几套
  arts: [ { /* 荣 */ }, { /* 枯 */ } ],
}
```

技能用 `castKind(unit)` 把"这一发是哪一式"报进快照（`SNAP_STRIDE` 第 15 位），
渲染层按 `pickBowArt(bow, castKind)` 查表取那一套，再从**那一套**里读
`idle / draw / arrow / anchor / nock / bowH / arrowLenFrac / burst`。
两式的画布尺寸和锚点都不同，混用会让弓飞到球外面去。

- 快照里只多了一个 `castKind` 数字，渲染层依旧是"只读快照、不做判断"。
- `kindArt` 与 skills.js 的 `TAOYAO.RONG_ART / KU_ART` 是同一张表的两种读法，
  `bow.mjs` 有一条断言把两者焊在一起。
- 查不到（越界 / 表少写一段）时回退第 0 套 —— 绝不返回 `undefined` 把渲染搞崩。

### 两帧必须对齐、而且必须都朝 +X（这一步不能省）

原始弓图有两类问题，都在 `tools/make-sprites.mjs` 里**一次修好**，
运行时不再记任何"哪张图要额外转几度 / 镜像一下"：

**① 两帧画布宽度不一样，各自居中画会横跳。**
荣是 116 vs 196（拉弓那张多一支箭），横跳 `(196−116)/2 = 40px`，动作直接废掉。
对齐量是**量出来的**：两帧的列不透明度剖面做互相关，并排除"箭矢所在的那几行"
（否则那支横箭会把结果拉偏）。实测荣偏移 25px、枯 38px。

**② 有一帧是镜像的：作者把「枯 · 平时」画反了手。**
实测那张是**弦在右、弓臂鼓向左**，而它自己的「拉弓」那张、以及荣的两张
都是弦在左、弓臂朝右。也就是说：球一举弓就是反的，一**拉弓整把弓还会左右翻个个儿**。
构建脚本会把方向不对的那一帧**左右镜像**过来 ——
注意**镜像 ≠ 转 180°**：弓上下有别（弓梢、握把装饰），转 180° 会把上下也翻掉。

判定"弓朝哪边"的启发式放在 `tools/lib/bow-facing.mjs`，
**构建脚本和 `bow.mjs` 诊断共用同一份**（各写一份的话，结论会悄悄不一样）：

- 弓没有头尾那种质量特征（弦几乎没重量），所以**不能用重心判**；
- 信号 A：弓梢（最上/最下两行的不透明像素）连成弦，比较弦与**全图不透明重心**的左右；
- 信号 B：逐行找"最细的一组（弦）"与"最宽的一组（弓臂）"，看弓臂在弦的哪一侧；
- 两个信号**必须一致**才下结论。不一致就报错让人看图，**绝不猜** ——
  猜错就是整把弓反着画。

```
assets/src/taoyao/bow_idle.png    ┐
assets/src/taoyao/bow_draw.png    ├─ 各自摆正 → 对齐 → assets/characters/taoyao_bow_{idle,draw}.png
assets/src/taoyao/arrow.png       ┘        + taoyao_arrow.png

assets/src/taoyao/ku_bow_idle.png ┐  ← 这张是镜像的，构建时自动左右翻转
assets/src/taoyao/ku_bow_draw.png ├─ → assets/characters/taoyao_ku_bow_{idle,draw}.png
assets/src/taoyao/ku_arrow_raw.png┘        + taoyao_ku_arrow.png（原图竖着、箭尖朝上 → 转 90°）
```

### 锚点与尺寸（改数值不用动代码）

**每一套美术各自带一份**这几个字段（两式的画布不同，不能共用）：

| 字段 | 含义 |
|---|---|
| `anchor` | **球心**落在这块画布上的比例位置。弓绕它旋转，所以它决定"球握在弓的哪个位置" |
| `nock` | 搭箭节点（那支搭好的箭的箭尾）在画布上的比例位置 |
| `bowH` | 弓的绘制高度（**世界单位**）；宽度按原图比例，绝不拉伸 |
| `arrowLenFrac` | 箭矢长度 ÷ 弓高。**飞出去的箭也读这个值**，所以搭在弓上的箭和射出去的箭永远等长 |
| `burst` | `{ count: 5, spreadDeg: 24.06 }` —— 五连发总共几发、张角的一半。**只有荣有**，枯是 `null` |

实测值（都由构建工具量出来，**别手改**；改完美术重跑工具、抄它打印的数）：

| 套 | 画布 | anchor | nock | arrowLenFrac |
|---|---|---|---|---|
| 荣 | 196×568 | (0.426, 0.5211) | (0.0051, 0.5211) | 0.3415 |
| 枯 | 214×589 | (0.5374, 0.5059) | (0.0514, 0.5059) | 0.3243 |

> `anchor.y` 必须等于 `nock.y` —— 也就是**球心要落在搭箭那一行上**，
> 否则箭会从球的旁边而不是身上射出去。smoke 里有一条断言守着这个几何前提。
>
> `bowH = 140`：球的直径是 32，弓是 1:4.96 的细长弓，所以这个数必须比球大不少 ——
> 球在弓的正中、上下各伸出一截弓臂。**这是观感参数，改一个数就能换。**
> 用 `node tools/preview-bow.mjs` 出图（一行 = 一套弓，一列 = 一个动作状态），
> 不用开浏览器。

### 箭矢：搭在弓上的箭 = 飞出去的箭

飞行的箭矢不再是程序化光点，而是**同一张 `taoyao_arrow.png`**（枯用 `taoyao_ku_arrow.png`）。
弹道通过 `sprite` 参数带一张贴图（引擎登记进 `projSpritePalette`，
快照里只存一个下标），渲染层按飞行方向 `atan2(dirY, dirX)` 旋转着画。
长度直接问**单位身上挂着的那套弓配置**（`bowH × arrowLenFrac`），
所以撒放那一瞬间接得上，改 `bowH` 也不用两头改。

> **一处刻意的例外**：箭矢长 47 世界单位，而它的判定半径只有 5。
> 这违反了项目"视觉尺寸必须等于判定尺寸"的规矩（那条规矩是为**场地物件**立的 ——
> 质点和细线会因为画得比判定粗而"看着没碰到却在掉血"）。
> 箭是**高速弹道**（500 单位/秒，每帧走 8.3 单位），长条视觉 + 圆形判定是常规做法；
> 把判定也拉成 47 长会实质改变命中率。**这一条等你定**：要严格一致的话我改成胶囊判定。

### 弹道贴图：蝙蝠与两枚能量弹（这一轮新加）

同一套机制（`sprite` + `spriteLen` + `spriteGlow`）也接上了另外三张图，
配置写在 **`skills.js` 的技能参数**里（不属于球种，因为它们是技能放出来的东西）：

| 图 | 用在哪 | `spriteLen` | 判定直径 | 光晕色 | 呼吸 |
|---|---|---|---|---|---|
| `yuncai_bolt.png` | 晕彩「魔弹」（普通那颗魔力球） | 20 | 12 | `#a855f7` 紫 | 不 |
| `tina_bolt.png` | 缇娜「魔力霰弹」 | 24 | 10 | `#f43f5e` 猩红 | 不 |
| `tina_bat.png` | 缇娜「蝙蝠」 | 8.5 | 10 | `#dc2626` 红 | **是** |
| `taoyao_arrow.png` | 映霞[荣]（含五连发） | 47.8 | 10 | `#ec4899` 粉 | 不 |
| `taoyao_ku_arrow.png` | 映霞[枯] | 45.4 | 10 | `#64748b` 灰墨 | 不 |

- **尺寸是作者定的观感参数**：改过三轮 —— 魔弹 30 → 15（"改成现在的一半左右"）
  → **20**（"魔弹尺寸统一改到 20"），蝙蝠 34 → **8.5**（"改成现在的四分之一"）。
  20 正好等于魔弹第三发光柱的粗细（`laserWidth`），两种形态的尺寸感统一。
  ⚠️ 蝙蝠的图**比判定小**（可见全长 8.5、判定直径 10）——
  要是觉得"看着没碰到却在掉血"，两条路：把图调回去，或者把 `r` 一起改小
  （后者是平衡改动，会改命中率）。`art-proj.mjs` 里有一条提示。
- 三张新图的方向同样是**构建时**统一成 +X（能量弹尾迹在左、亮核在右 → 不用转；
  蝙蝠头朝左 → 转 180°），运行时只管按飞行方向转。
- 晕彩的**第三发光柱不套贴图** —— 它是光柱，渲染层按 `beamLen / width` 程序化画。
- 分裂弹（棱镜的光门）会把母弹的贴图、光晕色与呼吸开关**一起继承**给碎片
  （`_splitProjectile`）；不继承的话碎片会静默变回程序化光点。
- **贴图要在开战前预热**（`preloadProjSprites(battle)`，在 `ui-battle.js` 里
  "整局算完"之后调用）：弹道是模拟过程中产生的，`projSpritePalette`
  要跑完才有内容；而本项目恰好是"先算完整局再播放"，所以这时能一次拿全。
  不预热的话，某种弹道**第一次出现的那一两帧什么都不画**
  （渲染层对没加载好的贴图是"宁可不画"），看着像"第一发没有特效"。

### 弹道贴图的光效环绕 +（只给蝙蝠的）透明度呼吸

两件事都只作用于**贴图弹道**（箭矢 / 蝙蝠 / 能量弹），
数值集中在 `render.js` 文件头那几个常量里，改一处全改：

| 常量 | 值 | 含义 |
|---|---|---|
| `PROJ_GLOW_ALPHA` | 0.30 | 光晕中心的不透明度峰值（"不用做太过强烈"） |
| `PROJ_GLOW_RX` / `RY` | 0.55 / 0.95 | 光晕椭圆的两个半轴 ÷ 图长、÷ 图高 |
| `PROJ_ALPHA_MIN` / `MAX` | 0.25 / 0.40 | **呼吸**区间：图的不透明度在这两头之间浮动 |
| `PROJ_PULSE_HZ` | 1.1 | 每秒呼吸几个来回 |
| `PROJ_GLOW_FLOOR` | 0.45 | 呼吸时，光晕暗到峰值的这个比例为止 |

**"谁在呼吸"是一个显式开关，不是全局行为** —— 作者的要求是
「只有蝙蝠有透明度呼吸效果，其他特效均不要制作透明度呼吸」：

| 配置 | 表现 |
|---|---|
| 该弹道的参数里 `spritePulse: true`（目前**只有蝙蝠**） | 图与光晕的不透明度在 25%~40% 之间来回浮动 |
| 没配 | 图**完全不透明**（1.0）、光晕恒为峰值，整枚弹道一动不动 |

- 开关从技能参数一路带到调色板条目（`spritePulse` → `palette[].pulse`），
  渲染层只看这一个布尔值 —— **不按弹道种类写 `if`**，以后想让别的弹道也呼吸
  只要在它的参数里加一行。smoke 里有一条断言要求这个字段是**显式 boolean**：
  要是哪天管道漏了它，渲染层会当成"不呼吸"，蝙蝠就静默地不呼吸了（不报错）。
- **相位用帧号算，不用墙上时钟** —— 渲染层只读快照（见文件头）。
  用 `performance.now()` 的话，一按暂停弹道就继续明暗闪、拖进度条也回不到同一帧的样子。
  `art-proj.mjs` 有一条断言守着"同一帧重画两次的透明度完全一致"。
- **光晕是椭圆**而不是圆，贴着图的形状 —— 箭是 47 单位的长条，
  用圆会把它裹成一大团；弹是圆球，椭圆正好。
- 光晕颜色来自每个技能的 `spriteGlow`。**必须挑中等饱和度的颜色**：
  场地是浅色方格纸（`#fdfcf7`），淡白的光晕在白纸上等于没画。
- 搭在弓上的那支箭（五连发的扇形）**也不参与**：它是武器的一部分
  （由 `_bow` 画），跟着闪会让弓看起来在漏电。
- 寿命末尾的淡出（`fade`）与呼吸是两回事：那是"快消失了"。
  诊断统计呼吸区间时要先把淡出中的那几帧筛掉，否则会量到 0.000。

> **看效果用 `node tools/preview-proj.mjs`**（出 `tools/preview-proj.png`）：
> 一行 = 一张贴图，一列 = 一个飞行方向（0/90/180/270°），
> 图上叠了**判定圆**和**飞行方向箭头**，还按 render.js 的比例画了那圈光晕，
> 透明度也按真实规则画（呼吸的取区间中点，其余完全不透明）。
> **这张预览的背景就是游戏里的浅色方格纸** —— 光晕是半透明的，
> 在深色背景上好看不代表在白纸上好看（这一条是改预览时踩到的：
> 之前两张预览都用深色底，参照系是错的）。
> 数字（`spriteLen` / 判定直径 / 光晕色 / 呼吸开关）取自真实对局的快照，
> 不是从配置另抄一份。

### 开华（形态强化）：爆发特效 + 屏幕抖动

晕彩血量降到 500 以下时触发「开华」。作者 2026-10 的要求是
「特效稍微显眼一点，并且伴随轻微的屏幕抖动」，所以这一版做了四件事：

| 部分 | 内容 | 数值（都在 `render.js` 文件头，素材编辑器里能拖） |
|---|---|---|
| **一次性爆发** | 三层彩色光环（紫 / 蓝 / 粉）+ 中心闪光圆盘 + 8 根放射细线 | `BLOOM_RING_ALPHA` 1.0（原来 0.85）、`BLOOM_RING_WIDTH` 6.5（原来 4）、`BLOOM_FLASH_ALPHA` 0.5 |
| **持续时长** | 34 帧（≈0.57 秒）；普通事件共用 22 帧 | `BLOOM_LIFE` |
| **常驻形态光晕** | 开华之后脚下一直有：一层径向柔光底 + 三条旋转弧 | `BLOOM_GLOW_ALPHA` 0.34（原来没有底光）、`BLOOM_ARC_ALPHA` 0.34（原来 0.18） |
| **屏幕抖动** | 整场（场地 + 球 + 特效）一起晃，像镜头被震了一下 | `SHAKE_MAX` 3.2 世界单位（≈4 屏幕像素）、`SHAKE_FRAMES` 20 帧、`SHAKE_HZ` 14Hz |

两条硬要求（不然就是"暂停了画面还在晃"这种经典 bug）：

- **抖动跟着帧号算，不跟墙上时钟** —— 渲染层只读快照（见文件头）。
  `_screenShake(battle, f)` 用"当前帧 − 开华事件帧"得到 age，平方衰减 + 正弦位移，
  所以暂停会冻在那一帧、拖进度条也会回到同一状态。
- **不叠加**：几个晕彩同时开华时取**最强的那一次**，而不是把位移加起来 ——
  加起来会变成"晃得看不清"，而作者要的是"轻微"。

> **看效果不用打对局**：`node tools/preview-bloom.mjs` → `tools/preview-bloom.png`，
> 把爆发按时间切成 6 格并排画出来，每格标注**那一帧的抖动位移**。
> 几何调的是 `render.js` 导出的 `bloomBurstSpec(t)` —— **和游戏里画的是同一份公式**，
> 预览不会和实际效果漂（本项目在"五连发扇形"上吃过一次亏：预览 14°、实际 24°）。
>
> 抖动可以在战斗界面控制条上关掉（「屏幕抖动」勾选框，偏好存在 `prefs.js`）——
> 有人看镜头晃会不舒服，所以给了开关。

## 素材编辑器（调尺寸 / 透明度 / 光晕 / 平衡数值，直接写回配置）

`http://localhost:5173/assets-editor.html`。

**必须先跑 `node tools/serve.mjs`** —— 写回要走本地开发服务器的
`POST /__edit` 接口。直接双击 html 只能看、不能存（页面上会明确提示）。

一屏三块：左边选素材、中间实时预览、右边旋钮。

  - 拖圆的**中间** → 移动它（改的是"图相对判定中心的偏移" `spriteOffX/Y`）

  画面上还会画一条从判定中心到图中心的连线，偏移一目了然。
- **右边**：滑块 + 数字框 + 取色器，改动过的字段左边会亮一条橙边；
  右上角常驻「● 未保存 N 项」。
- **保存**：右上角「一键保存」（或右栏那个，或 **Ctrl/Cmd + S**）——
  一次把**所有**改动过的字段写回 `js/*.js`，成功后会列出
  `文件:行号  键: 旧值 → 新值`，并更新"已落盘"的基准值
  （所以保存后"放弃改动"回到的是刚保存的那份，待写回列表也清空）。

左侧清单最后一组就是它，**24 项素材里的 9 项**：

| 项 | 改什么 |

**"实时"体现在两处：**

1. **预览区变成一个数值面板**（`js/balance.js`）。左边是原料，右边是**按当前值实时算出来的结论**：
   能挨几下、撞死一个 1500 血的目标要几次、每个技能每秒打多少、打空一个 1500 血的晕彩要几秒。
   改一个数，右边立刻重算 —— 不然"75 改成 150"到底意味着什么，光看输入框是没有体感的。
   裁光那种**每帧**结算的接触伤害会额外折成每秒（×60 帧）列出来，
   否则 1 点伤害看起来像"微不足道"。
2. **保存后游戏页会弹「素材已更新 · 点击刷新」**。引擎在页面加载时把
   `balls.js` / `skills.js` 读进内存，改完源码它不会自己知道
   （就算重新 import 也是第二个模块实例，引擎手里还是旧的那份）——
   所以**刷新这一步躲不掉**，那就别让作者自己去想 Ctrl+F5：
   编辑器保存成功后往 `localStorage` 写一条消息，别的标签页会收到
   `storage` 事件（浏览器原生、同源跨标签页），游戏页据此弹出小条，
   上面还写着**改了哪几个字段、从多少变成多少**。点「点击刷新」即生效。

三条自我约束（都是"不要给自己挖坑"）：

- **不收录诊断夹具那几颗测试球**（`test` / `test_skill`…，它们已经搬去 `tests/lib/test-balls.mjs`）：
  `tests/diag/skill3.mjs` 等守卫把 50 / 200 / 100 这些数写死了，
  "编辑器能改"和"守卫要求不变"会互相打架。要调的是正式角色。
- **不收录比值/表达式**（`damageMul: 4 / 3`、`miniDamageMul: 1 / 3`）：
  写回只支持具体数值，改成 1.333333 会丢掉"这是三分之四"的语义。
- **负数/荒谬值挡在控件层**：每个字段都带 `min/max`，
  滑条与数字框都会夹住（自检里有一条专门验"每个数值字段都有取值范围"）。

> **为什么字段上要带一个 `pick`**（例如 `pick: 'YUNCAI.modan'`）：
> 数值字段的 key 都很短（`damage`、`cd`、`hp`），光靠它推不出"属于哪个技能"。
> `pick` 是一个指向真实导出对象的点分路径，编辑器按它读现值。
> 写成数据而不是在界面代码里手写映射表，是因为**手写清单忘登记**已经出过一次事
> （见"踩到的坑"第 42 条）；写成数据还能被自检逐个核对路径是否真的取得到值。

**数字数组**（`dmgByStage: [1, 2]` 这种一维数值）也是可编辑的：
新增了 `nums` 类型，界面上是一个文本框，写 `1, 2`（中文逗号也认），
写回时格式化成 `[1, 2]`；空数组和非法数字会被拒绝 ——
不能因为手滑把一档伤害改没了。

### 判定半径与贴图偏移

这一轮新开的两个旋钮，都是为了解决"看到的位置 ≠ 判定的位置"：

| 字段 | 含义 |
|---|---|
| `r`（每个弹道自己的） | **判定半径**。判定中心就是弹道位置，物理上用它做碰撞 |
| `spriteOffX` / `spriteOffY` | **贴图相对判定中心的偏移**（世界单位，弹道局部坐标：+x 朝前、+y 朝飞行方向右手侧） |

- 0 = 图正好套在判定圆上。彗星状的图（亮核在右、尾迹在左）把 `x` 调大一点，
  亮核才会压在判定圆上；否则会出现"看着打到了却没伤害 / 看着没碰到却掉血"。
- 渲染层把**图和光晕一起挪** —— 只挪图不挪光晕的话，会出现
  "光在一个位置、图在另一个位置"（`art-proj.mjs` 有一条断言专门守这个）。
- 偏移跟着弹道一起旋转（它在弹道的局部坐标系里），所以弹道转向时图不会甩出去。
- 分裂弹（棱镜的光门）会把偏移**一起继承**给碎片。
- ⚠ **判定半径是平衡数值**：改它会改命中率。编辑器里标了「⚠ 平衡数值」，
  `smoke.test.mjs` 还有一条通用不变量守着"半径必须在 1~40 世界单位"。

**写回是怎么保证安全的**（这是这个功能最容易出事的地方，改的是人手写的源码）：

| 保证 | 做法 |
|---|---|
| 只能改登记过的字段 | 字段清单在 `js/asset-schema.js`，服务器只认这些 id，别的直接 400。**清单每次保存重新读**（带缓存戳动态 import），所以加了新旋钮不用重启服务器。**写回实现本身也每次重新读**（这一轮加 `nums` 类型时踩到：正在跑的服务器是启动时 import 的旧版，保存直接 409「不认识的字段类型：nums」） |
| 不会改错地方 | 每个字段是"**唯一锚点 + 键**"；锚点必须全文唯一、窗口内该键必须只出现一次，否则**拒绝写入**并说明原因。⚠ **锚点里不能带会被改的那个值**（写回后锚点自己就没了，见"踩到的坑"第 45 条） |
| 不会把注释当代码 | 找键时先把注释挖空（等长替换、偏移不变）—— 注释里写了 `spritePulse = …` 会被误当成代码（实测踩到） |
| 不会改坏格式 | 只替换"值"那一段，逗号、分号、行尾注释原样保留；值以 `[` 开头时按配对括号扫到 `]`（数组里的逗号不是值的结束） |
| 改了一半更麻烦 | 一次请求里同一个文件只写一次；任何一条失败就整份不写 |
| 有后悔药 | 写回前留一份 `js/*.js.bak`（**本地保留、但不发布** —— 发布脚本会跳过 `.bak`/`.tmp`/`.orig`/`.swp`，否则等于把旧版源码一起公开出去） |

> **如果点保存报"服务器没有 /__edit 接口"**：说明你正跑着的 `serve.mjs` 是旧版
> （这个接口是后来才加的）。关掉那个窗口、重新 `node tools/serve.mjs`、刷新页面即可。
> 页面会直接把这句话写在状态区里，不会让你对着一个"写回失败"发呆。

配套的两个工具（都在 `tools/`）：

- `node tools/check-asset-schema.mjs` —— **旋钮自检（601 项）**：
  把每个字段在真实源码上试算一遍（锚点唯一 / 键唯一 / 往返一致 / 只改一处），
  反向验证"锚点不存在、同名键有多个、窗口内找不到"都必须报错，
  另外核对**每个 render 字段的导出名都真的存在**、**每个数值字段的 `pick` 路径都真的取得到值**
  （取不到现值 = 界面上一排空白框，见"踩到的坑"第 42 条）。加新旋钮忘了配锚点，这里立刻红。
- `node tools/check-boot.mjs` —— 顺带把编辑器页面也开一次，
  并把 24 个素材**逐个点一遍**、**逐个数一遍数值框**（空白框直接判失败）。
  任何一个素材的控件生成或预览绘制出错都会被抓到。

> 为什么不用"路径解析 + AST 改写"：这些配置是人手维护的源码（大量注释、
> 模板字符串、算出来的常量），上 AST 成本太高；锚点方案简单、可校验，
> 失败时能明确报错而不是悄悄改错地方。

## 音效

**程序化合成，不需要任何音频素材** —— 用 Web Audio 现场生成波形
（振荡器 + 噪声 + 包络），因此不牵扯任何素材版权，参数即代码、随手可调。

架构位置：**和 `render.js` 平级的一层"消费者"**。
引擎一行都没改 —— 音效挂在已有的事件流上，和画面用同一份数据，
所以它天然跟随"播放头"：**暂停就停、回放就重来、倍速自动节流**。

战斗界面控制条上有「音效」开关与音量滑块（默认关闭），偏好存在 `js/prefs.js`。

### 三个必须守住的点

| 坑 | 做法 |
|---|---|
| **自动播放限制** | 浏览器在用户手势前不许出声，`audio.unlock()` 必须由真实点击触发（首次 pointerdown/keydown 时解锁） |
| **事件洪流** | 裁光的质点/细线一秒能出 **60 条** hit。按类型设最小间隔（`MIN_GAP`），持续伤害单独卡到 200ms；再加同时发声上限 `MAX_VOICES = 8` |
| **拖动进度条** | 播放头一次前进超过 `MAX_STEP_FRAMES = 24` 帧就判定为"跳转"，**整段不发声** —— 否则拖到末尾会炸出一片声音 |

### 声音怎么对应事件

- **打击**：见下面「打击感」一节（作者 2026-10 的专项要求）
- **开华**：上行四音琶音（对局里最重要的瞬间）
- **细线进阶**：阶段越高音越高，能听出"线在变强"
- **细线爆炸**：低频冲击 + 噪声
- **发射**：魔力球 / 激光 / 分裂体各有不同音色
- **声场定位**：按事件的 x 坐标做立体声左右分布（`StereoPanner`），跨度实测 1.39

### 打击感（伤害越高，反馈越强）

作者 2026-10 的要求是「增强小球攻击命中时候的打击感（伤害越高反馈越强）」。
"打击感"不是把音量拧大 —— 只拧音量听起来像"同一拳离麦克风更近了"。
一记打击由**三层**叠出来，三层用**同一个权重**放量、放长：

| 层 | 是什么 | 负责什么 |
|---|---|---|
| ① 脆 | 极短的**带通**噪声（低通 5200~7600Hz + 高通 600Hz） | "打到了"（没有它听起来像隔着一层布） |
| ② 实 | 三角波，音高从 `base` 往下滑 45% | "多轻多重"（近战 base 220、弹道 420） |
| ③ 沉 | 60~110Hz 的正弦 | "胸口那一下"（权重 < `HIT_SUB_FLOOR` 0.25 时不出，轻碰本来就该轻） |

伤害 → 权重的映射是**对数**的（`hitWeight()`，`HIT_SOFT = 30`、`HIT_HARD = 300`）：

```
伤害   0     20     66     100    200    300+
权重   0.00  0.21   0.49   0.61   0.85   1.00
```

原来是一条线性 `dmg / 300`，两个毛病：66 的碰撞伤害只拿到 0.22
（而它恰恰是整局里响得最多的一声，"最常听到的打击"永远停在最轻那一档）；
300 以上全压成 1.0（200 的技能和 400 的爆炸听起来一样重）。

另外总线接了一级**软限幅**（`DynamicsCompressor`，threshold −12dB / ratio 6）：
混战时十几下打击叠在一起也不会削顶爆音，而限幅本身就让"重击"更结实
（动态是打击感的另一半）。没有这个节点的环境自动跳过（无头诊断里就是）。

每帧持续伤害（裁光的质点/细线）**不走这一套**：它有自己的 200ms 闸门和
一个固定的轻音，否则"每帧一次的重击"会把整套打击感淹掉。

> **视听共用一套刻度**：`render.js` 的伤害飘字字号也调 `hitWeight()`
> （见下面「伤害飘字」一节）。两边各算一套的话，同一下重击会出现
> "看起来比听起来轻"的错位。

### 诊断

`tests/diag/audio.mjs`（46 项）—— 音效没法用耳朵验证，所以**伪装一个
AudioContext 把发声调用全部录下来**再核对：建了多少声源、什么频率、
多大音量（记的是**峰值**：只看最后排程的值会全是 0.0001 的衰减尾巴）、
左右多偏。重点盯几件容易悄悄坏掉的事：

```
✅ 持续伤害没有逐条发声（被节流）  — 103 条 tick → 44 个声源
✅ 一次跳过 2900 帧时完全不发声  — 0 个声源
✅ 整局下来引擎自己的发声名额从未超过上限  — 峰值 8 / 上限 8
✅ 关闭音效后一声不出  — 0 个声源
✅ 伤害越高音高越低  — 214 → 172 → 121 Hz
✅ 伤害越高音量越大  — 0.098 → 0.153 → 0.220
✅ 伤害越高余音越长  — 89 → 197 → 300 ms
```

> 这个脚本抓出过一个真 bug：最早用 `setTimeout(…, 400)` 回收"同时发声数"，
> 但那是**墙上时间**，而声音活在 `AudioContext.currentTime` 时间轴上。
> 倍速播放时两者差好几倍，名额会被永久占满 —— 表现为"越打越没声音"。
> 现在按音频时间记账（存每个声源的结束时刻）。

## 伤害飘字

作者 2026-10 的要求是「加大加粗伤害文字，把伤害文字改为显眼一些的红色」。
原来是最普通的深灰 `bold 12px`。现在画一个数字要做这些事，全是
`render.js` 文件头里的常量（素材编辑器 →「界面文字 · 伤害飘字」里能拖）：

| 部分 | 做法 | 常量 |
|---|---|---|
| 更大更粗 | 基准 19px / 字重 800（原来 12px + bold） | `DMG_FONT_PX`、`DMG_WEIGHT` |
| 显眼的红 | 鲜红填充 `#e11d1d` | `DMG_COLOR` |
| **浅色描边** | 先描边后填充，宽 3.4、圆角接头 | `DMG_OUTLINE`、`DMG_OUTLINE_W` |
| 出现瞬间放大 | 第 0 帧 1.35× → 7 帧收回 1.0 | `DMG_POP`、`DMG_POP_FRAMES` |
| 伤害越高字越大 | 满权重时再放大 40% | `DMG_SIZE_GAIN` |
| 上升距离 | 22 帧里升 24 世界单位 | `DMG_RISE` |

- **描边才是"显眼"的真正来源**：场地是浅色方格纸、球是深色贴图，
  红字压在球面上会糊、压在纸上会飘，那一圈浅色描边把两种情况都解决了；
  填充色只负责"它是红的"。
- 字号跟着 `hitWeight()`（音效那一份）走，和打击音的轻重是同一个刻度。
- 血量代价（晕彩的析光）走的是同一个函数，只是换成冷色小字
  （13px / `#7c3aed`），免得被误读成"又挨打了"。
- **游戏与素材编辑器预览共用 `drawDamageNumber()`** —— 预览另抄一套的话，
  作者照着预览调完，实际打出来又是另一个样子（本项目在"五连发扇形"上吃过这个亏）。

诊断：`tests/diag/dmg-text.mjs`（29 项）。截不了图，所以换成一个
**带变换栈与样式快照的记录型上下文**：把每次 `fillText` / `strokeText`
连同当时的 `font / fillStyle / strokeStyle / globalAlpha / 变换`一起录下来再核对 ——
颜色是不是那支红、是不是先描边后填充、字号是否随伤害单调、
放大是否绕锚点收回到 1.0、每个数字是否画在"命中点 + 该帧应有的高度"上、
逐帧是否真的在往上飘、关掉「显示伤害」后是不是一个字都不画。

### 为什么不用 `git push`

**本机 git 的 HTTPS 传输是坏的**：`git ls-remote` 都过不去，报
`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS` ——
连不涉及凭据的请求都失败，说明是沙箱挡了 schannel，跟 token 没关系。
Node 自己的 TLS 栈是好的，所以改走 **GitHub Git Data API**：
`create blobs → create tree → create commit → 移动分支 ref`。
另外两个沙箱限制也一并绕开：管道 stdio 的 `child_process` 会 EPERM、Git Credential Manager 起不来。

### 发布流程踩过的坑

1. **空仓库上 Git Data API 一律 409**（`Git Repository is empty.`）——
   刚建好的仓库必须先有一次提交才能用 blobs/trees。
   脚本会对这种情况自动"播种"一次初始提交（用 Contents API 写 `.nojekyll`）。
2. **ref 端点必须是 `/git/refs/heads/main`（复数）** ——
   写成单数会返回一个看起来像权限问题的 404，让人白查一轮 token。
3. **回读时 ref 上是 `.object.sha`（提交的 sha），不是 `.object.tree.sha`** ——
   要数文件得先取提交、再从提交取 tree。
4. **Pages 首次生效要 1~2 分钟，且全站 `max-age=600`** ——
   改动最多 10 分钟才可见；回读时给 URL 加时间戳绕开缓存，
   否则会把"缓存"误判成"没推上去"。
5. **回读"通过"不等于内容是新版本 —— 加了时间戳也可能拿到旧缓存**（实测）——
   发布后立刻回读，10 个资源全部 200、类型全对、体积也非 0，
   脚本报"验证通过"。但把两次回读的体积列出来一比就露馅了：
   引擎 97 KB → 105 KB、技能表 30 KB → 47 KB、文档 48 KB → 60 KB。
   **第一次拿到的其实是推送前的旧缓存** —— 因为"推送完成"和
   "CDN 各节点刷到新版本"之间有时间差，而时间戳参数只绕过了**浏览器**缓存。
   致命之处在于：旧的 `balls.js` 配上新的 `index.html` 看起来**完全正常**，
   页面能开、不报错，只有进游戏才会发现少了角色，
   光看响应码和 content-type 永远发现不了。
   **修法：回读必须抽查"内容本身"**，而不是只抽查"能不能拿到"。
   现在 `verify-pages.mjs` 会从本地 `js/balls.js` 现取球种清单，
   逐个确认线上文件里真的存在 —— 判据从本地现取，
   **以后加新角色不用改这个脚本**，也不会有人忘了加。

### 防泄漏闸门

发布脚本内置一道闸门，**上传前**扫描所有待传文件，命中就拒绝上传：

- 本机绝对路径（用户目录，以及本机几个专有目录下的路径）
- token 形状（几种常见的 GitHub 令牌前缀）与私钥头

两个设计要点，都是被自己坑出来的：

- **规则只有一份**（`LEAK_PATTERNS`）。自测若复制一份正则，
  闸门改了而自测没改，就会出现"自测通过但闸门失效"。
- **自测样本在运行时拼出来**，不能把泄漏样本写死在源码里 ——
  否则闸门扫到自己就把整个仓库拦下了（第一版就是这么翻车的，
  连着拦了三次：先是脚本注释里的真实路径，然后是自己的两个样本）。

> 闸门不是摆设，前后拦下过四次：发布脚本注释里的本机路径、
> 它自己的两个自测样本、以及本文档里为举例而写的路径。
> 最后一类属于**误报**，但没有为它开白名单（白名单会削弱闸门），
> 而是把文档改成用文字描述 —— 规则保持严格，误报改内容。

## 开发中踩到并修掉的坑（都已写进测试，防止回归）

### 渲染：画面被拉伸 / 场地没显示全

1. **CSS `width:100%` 把绘图缓冲区二次拉伸** —— 缓冲区按 `clientWidth × dpr` 算，
   浏览器又把它拉到 CSS 宽度，于是 `sx ≠ sy`，画面被非均匀拉伸。
   表现：小球变形、**血条被拉成怪异的矩形**（用户反馈的"不明的矩形"就是这个）。
   **修法：CSS 只做"不超出容器"的保险，宽高由 JS 显式定死；
   `draw()` 改用 `ctx.scale(s, s)`，横纵共用同一比例。**

2. **相机没有跟着场地走** —— 把场地缩小到半场后，它落在世界中心、
   四周被画布边界截断，看起来就是"场地没显示全"。
   **修法：按场地包围盒取景（`setArena` → 相机把包围盒映射到整块画布），
   场地自然居中铺满；顺带半场时画面整体放大一倍。**

56. **相机比例用的是 CSS 像素，但绘制发生在缓冲区坐标系上 —— 场地只铺满画布的 1/dpr** ——
    `resize()` 里：

    ```js
    const scale = dispW / boxW;                 // CSS 像素 / 世界单位
    cv.width = Math.round(dispW * bufScale);     // 缓冲区又乘了 bufScale（dpr）
    this.camScale = scale;                       // ← 少了 ×bufScale
    ```

    而 `draw()` 是 `ctx.scale(camScale, camScale)` 作用在**缓冲区**坐标系上，
    所以 camScale 必须表达"缓冲区像素 / 世界单位"。少乘一个 dpr 的后果是
    场地只铺满画布的 `1/dpr`：

    | 屏幕缩放 | 场地占画布 | 观感 |
    |---|---|---|
    | 100%（dpr 1） | 100% | 看不出问题 |
    | 125% | 80% | 右边一条空白 |
    | **135%（作者的机器）** | **74%** | 战场明显铺不满画布 |
    | 200% | 50% | 空白比战场还大 |

    **为什么一直没被测出来（这条最值得记）：**
    smoke 里其实**已经**在用 `dpr = 2` 跑了，断言却是
    `camScale × boxW ≈ cssW` —— 而 `camScale` 当初就是按 `dispW / boxW` 定义的，
    这条断言**按构造必然成立**，等于把实现原样抄了一遍当判据。
    另一条"等比不失真"比的是 `cv.width / boxW` 与 `cv.height / boxH`，
    两者都是缓冲区口径，也一起成立。
    两条都在测"我算出来的数对不对"，没有一条问"**场地到底盖住画布了没有**"。

    > **教训：断言要落在可观察的结果上，不能复述实现。**
    > 现在这条写成 `camScale × boxW === cv.width && camScale × boxH === cv.height`
    > —— "场地包围盒正好铺满绘图缓冲区"，和实现怎么算无关，dpr 多少都要成立。

    顺带：这个 bug 只在 dpr ≠ 1 的机器上看得见，所以**开发机是 100% 缩放的话永远发现不了**。
    修完之后作者那边战场会大一圈（135% 的机器上大约 +35%），那是把本来就该有的尺寸还回来。

    另外调试面板里 `camScale × boxW / dpr` 也要改成除 `_bufScale` ——
    缓冲区超过 `MAX_BUF_W` 时 bufScale 会被压低，那时除 dpr 就不准了。

### 物理：粘在一起 / 互相穿过 / 碰撞没伤害

3. **空间哈希的邻居遍历漏掉了"正上/正下"格子（最严重的一个）** ——
   写法 `for (let dy = dx === 0 ? 0 : -1; dy <= 0; dy++)` 在 `dx===0` 时
   `dy` 只取 0，于是**同一列的相邻格子永远不会被检查**。
   后果：处在上下相邻格子的两球**互相穿过对方**，实测穿透 16 单位、
   相对速度 -198 却毫无碰撞；同样原因也让它们**判定不到伤害**。
   表现就是"粘在一起""碰撞没伤害""方向不变"——三个症状同一个根因。
   **修法：只遍历"右/下"半边的邻域偏移 `[[0,1],[1,-1],[1,0],[1,1]]`，
   恰好覆盖 8 个邻居各一次，不重不漏，且与坐标正负无关。**
   （不要用"网格 key 比大小"去重：球被推到负坐标区时 key 的大小关系
   与格子方位不对应，会再次漏格。）

4. **边界夹紧会造出新的穿透** —— 球被推到场地外时，夹紧会把它朝质心拉回，
   几个球可能被堆到一起。碰撞解算在夹紧之前，于是帧末留下"叠着还在往里挤"的球对。
   **修法：夹紧之后补一次"只分离、不加冲量"的处理（`_relieveOverlap`）。**

5. **碰撞分离只迭代一次** —— 实测最大穿透能到 24.9 单位（球直径才 32），
   一帧修不完就继续叠着。**修法：交错迭代（分离 → 冲量 → 再分离…），并每轮重建网格。**

6. **分离与冲量分成两个独立阶段（改错了又改回来）** ——
   分离推开后冲量又可能把它们推回来。实测分阶段做法让重叠率从 13% 涨到 **55%**，
   肉眼就是"粘在一起"。**正确做法是交错迭代。**

7. **冲量后不保证真的在分开** —— 重球撞轻球时，按质量反比解出的冲量
   可能让轻球速度几乎不变，两球就贴合着一起走。**修法：给法向分离速度设下限。**

8. **擦碰后方向几乎不变（知觉问题，非 bug）** ——
   法向相对速度接近 0 时物理上确实只微转（实测约 4% 的碰撞转向不到 2°）。
   玩家看到接触却没看到偏转，会认为"撞了没反应"。
   **修法：接触后保证每个球至少以 8° 离开接触面；
   只对"仍在靠近"的球生效，弹开的球原样保留（否则对撞会被错误推向同一侧）。**

### 判定与胜负

6. **僵局破解器把攻击判定范围扩到了 230+、伤害倍率拉到 8 倍** ——
   结果是"两个小球隔着大半个屏幕、明明没接触却在掉血，伤害数字也对不上球本身属性"
   （碰撞伤害是 100，实际跳出 545、800）。这属于用假机制掩盖真问题。
   **修法分两步：先把判定范围改成永不扩大（没接触就是没伤害）；后来物理修好、
   确认不再需要兜底，就把整个破解器连同"饥饿"机制一起删掉了 ——
   现在伤害数值恒等于属性表/技能表里写的值。**
   （删掉之前先量过：13 个场地 × 3 种规模 × 4 个种子 = 156 场全部自然打出结果，
   中位 12.7 秒、最长 55 秒，零僵局。守卫脚本：`tests/diag/finish-rate.mjs`。）

7. **转向的每帧角度是小数，被当成整数表索引** ——
   `sinDeg(0.5)` 查 `SIN_TABLE[0.5]` 返回 `undefined`，整条速度向量变成 `NaN`，
   **小球直接消失且不报错**。撞墙偏转没暴露这个问题纯属运气。
   **修法：查表索引四舍五入；小数部分用累加器攒够 1 度再转。**

8. **成对碰撞冷却被每帧续期** —— 两个持续贴合的小球让冷却永远续期，
   全场只掉一次血。**修法：只有在确实造成伤害后才写冷却。**

9. **空间哈希的单元尺寸小于查询半径** —— 两个明明在攻击范围内的小球，
   因为落在斜对角的格子里而永远查不到对方，**完全静默零伤害**。
   **修法：网格单元尺寸改为 `max(40, 查询半径)`。**

### 边界与几何

10. **边界法线符号写反** —— 内法线下小球朝墙撞去时 `v·n` 是**负数**，
    而判定写成了 `vn > 0`。后果：速度永不反射、小球沿墙滑到角落停住，
    **2v2 在 300 秒里只发生 2 次碰撞**。

11. **圆形场地的法线约定与多边形不一致** —— 多边形分支指向场内，
    圆形分支却指向场外，导致小球沿圆周一直滑行、全部僵死到 300 秒上限。

12. **吸附到边界后判定失效** —— 用严格小于号判定穿透，小球被吸附到
    `距离 === 半径` 的临界位置后判定永远不成立。改为带容差判定。

13. **反射与挪位置的顺序错了** —— 先用夹紧后的位置取法线，位置可能已被挪到
    另一条边上，拿到的法线是错的。必须先反射速度、再挪位置。

14. **斜法线取整导致速率流失** —— 45° 边的内法线长度只有约 0.707 而非 1，
    反射按 `|n|²` 缩放速度、球球碰撞的冲量也被放大，菱形场一次碰撞掉 9% 速度。
    修法：完全弹性碰撞后按碰撞前的速率还原。

15. **单队场景不是有效对战** —— "存活队伍只剩 1 支"被当作胜利条件，
    因此只有一支队伍时会第 1 帧判定结束。**至少要有 2 支队伍**。

16. **冲量与位置分离的顺序错了 —— 小球有速度却一动不动（最新一个）** ——
    原本先做位置分离、再算速度冲量。但分离会把两球**正好推到"相切"**
    （distance === r1+r2），而冲量函数开头会判定"不再重叠"直接返回 ——
    冲量永远不生效；同时移动阶段每帧又把它们推到一起、分离再推回去，
    两者精确抵消。实测表现：**速度 120、整整一秒零位移**，球卡在相切位置。
    **修法：先算速度冲量、再做位置分离**（用同一份重叠信息）。
    同时给"贴切向滑行"（v·n≈0）的接触加一个最小出射角，
    否则运动仍会被分离推挤抵消。

17. **空间哈希的单元尺寸必须 ≥ 邻域能覆盖的最大距离** ——
    这条踩过三次，每次都因为改了球体尺寸或判定范围而失效：
    · 单元 40 + 3×3 邻域 ⇒ 只能覆盖 40 单位内的配对；
    · 曾把判定范围扩到 118 ⇒ 落在斜对角格子的配对永远匹配不上；
    · 曾把半径翻倍到 32（接触判定需 64）⇒ 距离 40~64 的配对全部漏掉。
    **修法：碰撞用的单元尺寸必须 > 2r（当前 r=16 取 40）。**
    每次调整球体半径或判定范围，都要回头核对这个约束。

18. **开局站位要把球留在场内** —— 简单环形排布会把靠外的球推出场地，
    被夹紧拉回后又互相叠住。**修法：环形分布 + 带边界检查的螺旋搜索**。

### 技能系统

19. **浮点秒数倒计时会让时长多出 1 帧（蓄力 2 秒实际 121 帧）** ——    原先把蓄力写成 `u.charge = 2.0; u.charge -= DT;`。
    `2.0` 连减 120 次 `1/60` 之后剩下的不是 `0`，而是 `1.4e-15` 这样的残渣，
    于是判定 `u.charge === 0` 要多等一帧才成立：
    · 蓄力实际跑 121 帧（2.0167 秒）；
    · 屏幕上还会出现 `chargeP = 0.999999999999999` 的进度环 ——
      "看着满了却没出发"。
    **修法：蓄力 / 冲刺一律按整数帧计时**（`chargeFrames` / `dashFrames`，
    见 `skills.js` 的 `CHARGE_FRAMES` / `DASH_FRAMES`）。
    引擎其它部分本来就是整数逻辑，这里补上就完全对齐了。

20. **用速度判断"动没动"，掩盖了"冲刺期间小球原地不动"（最隐蔽的一个）** ——
    冲刺分支原本以 `continue` 结尾，只负责**设定速度**，
    跳过了后面统一的位置积分 `u.x += vx * DT`。
    结果是：速度曲线漂漂亮亮（358 → 120 线性衰减）、
    状态机时序也对，但**球的位移恒为 0.00**；
    而且因为没动过，冲刺永远撞不到人（命中 0 次、击退 0 次）。
    之所以一直没被发现，是因为所有诊断都在采样 `u.vx / u.vy` ——
    **速度不等于位移，测速度测不出没位移**。
    **修法：冲刺分支不再 `continue`，只跳过"转向 / 阻力 / 区域减速"这些修正
    （用 `if (!dashing)` 包住），位移积分照常执行。**
    现在冲刺 120 帧共位移 472 单位，并且真的能撞到人。
    教训写进测试：`tests/diag/dash-move.mjs` 只读**快照里的位置**（即玩家看到的位置），
    不再读速度。

21. **状态帧数少 1 帧：在最后一帧就把 mode 改回去** ——
    冲刺跑完最后一帧时顺手把 `mode = 'normal'` 并抛出 `dashEnd`，
    于是 `mode === 'dashing'` 只被观察到 119 帧。
    **修法：把"收尾"挪到下一帧开头做**，让 `mode` 恰好覆盖 DASH_FRAMES 帧。
    同理，撞墙那一帧不能就标成 `charging`（那一帧球还在墙上、
    位置是这一帧刚夹紧过去的），否则蓄力会多算 1 帧 ——
    现在由 `core.js` 的状态机在下一帧统一进入 `charging`。

25. **"每帧覆盖速度"的机制会和撞墙反弹互相打架 —— 球贴墙抽搐后卡死** ——
    （用户报告：冲刺撞到墙壁后"在墙上抽搐一下，然后进入吸附状态"。）
    冲刺分支每一帧都会把速度重新写成 `dashVx/dashVy × 当前速度`，
    这是"每帧覆盖"而不是"只设一次"。于是撞墙那一刻：
    · 撞墙反射先把速度改成朝场内（正确）；
    · 下一帧冲刺分支又把速度覆盖回"朝墙里冲"（反射被整个抹掉）；
    · 球被推进墙里 → 被夹回原位 → 净位移恰好为 0。
    实测圆场里连续 **20 帧位移恰好 0.000**，而速度一直是 162 ——
    也就是用户看到的"抽搐 + 吸附"。
    更麻烦的是 `onWall` 技能此时因为 `dashFrames > 0` 拒绝触发，球永远爬不出来。
    **修法：撞墙对冲刺来说是终止条件 —— `_onWallTouch` 里先把冲刺结束掉
    （清 `dashFrames`、置 `mode='normal'`、抛 `dashEnd`），再让技能接手。**
    置成 `normal` 是关键：否则下一帧的"冲刺收尾"分支会把速度按冲刺方向还原回去。
    **刻意不清零速度**：上面刚做完的撞墙反射要留着，清零交给真正接手的技能；
    这样即使某个冲刺技能没配 onWall 接手技能，球也只是正常弹开，
    不会变成速度 0 永远停在墙上。

### 晕彩的七个技能

28. **"每帧 1 点"被合并成"-16"—— 为了防事件流爆掉而报了假数** ——
    裁光的质点/细线是逐帧掉血，60 次/秒的飘字会把事件流（6000 条上限）冲爆，
    所以我当初把 15 帧的伤害合并成一条事件输出。
    结果飘字变成 15×1+1 = "-16"，玩家读到的是"一帧扣了 16 点"，与设定完全对不上。
    **修法：事件逐帧如实输出真实数值（1 或 2）；防爆改成两道 ——
    ① 飘字节流交给渲染层；② 给持续伤害单独设事件上限
    （`MAX_TICK_EVENTS`，超了只扣血不发事件，免得把总上限吃光导致死亡/开华事件被丢）。**
    **教训：合并显示等于报假数。要省事件就省"事件数量"，不能改"数值"。**

29. **质点是按球心落的，不是按墙面接触点** ——
    （用户报告："质点生成的位置应该在墙壁上，即晕彩和墙壁接触的位置，
    而不是晕彩小球的中心"。）
    球被夹紧后**球心离墙面还有整整一个半径**，所以质点落在场地中间，
    连出来的细线看着像凭空画在场里。
    **修法：撞墙时把"球与墙面的接触点"算好传给技能。**
    坑在于这个接触点**不能拿 `clampToShape` 的返回值直接反推** ——
    它的三个分支语义并不一致：
      · 多边形·在内部：返回球心原位置；
      · 多边形·在外部：返回"球心被拉回场内"的位置；
      · 圆形·在外部  ：返回球心该在的位置（离墙面整整一个半径）。
    照任何一种推都会偏，实测偏 5~16 个单位。
    最后改用与分支无关的办法：**从球心沿朝墙方向一格格试探，
    取最后一个仍在场地内的点**（6 个场地实测距墙都是 0.50 = 试探步长）。
    **教训：一个被多处复用的函数，先写清返回值语义，再拿去反推别的东西。**

30. **场地物件没进快照 —— 回放开头会画出整局打完后的所有细线** ——
    （用户报告："这些细线都是斗蛐蛐刚开始就直接出现在场地上的"。）
    技能逻辑其实一直是对的（质点→质点→连线→两个质点消失），
    问题在渲染层：弹道一直是读**快照**的，而场地物件我图省事直接读了
    `battle.fields` —— 那是**模拟结束后的最终状态**。
    于是把进度条拖回 0 秒，画面上照样是整局累积下来的全部细线，
    看起来就像"开局凭空出现一堆线"。
    **修法：给快照加 `fields` 缓冲（`FIELD_STRIDE`），
    渲染层改读 `snap.fields`。**
    **教训：架构原则（"渲染只读快照"）不能因为"这个对象不会动"就破例 ——
    细线不会动，但它会**出现和消失**，一样要逐帧记录。**
    守卫：`render-yuncai.mjs` 断言"开局 30 帧内没有任何细线"、
    "每一帧画的线数 = 该帧快照里的线数"。

31. **同一个宽度有两种单位，激光被算成 0.016 宽（画不出来的头发丝）** ——
    `_spawnProjectile` 里 `w: p.width || (p.radius * 2)`：
    `p.width` 传的是**世界单位**（16），而 `p.radius` 是**定点数**（8000），
    两个来源单位不一致；快照又按定点数除了一次 `SCALE`，
    结果 `16 / 1000 = 0.016`，整根光柱只剩"外壳"那几像素，
    看起来就是"太细了"。
    **修法：`p.w` 统一以世界单位存放**（`p.width || p.radius / SCALE * 2`），
    快照不再二次换算；粗细只定义一处（`YUNCAI.modan.laserWidth`），
    判定半径取它的一半。
    **教训：同一个字段被两个来源赋值时，先把单位统一，再谈数值。**

32. **把"光"限定成"敌方的光"，导致细线永远停在第一阶段** ——
    设定原文是"细线会对'光'（**即晕彩的其他技能**）起反应"，
    也就是说"光"的定义就是晕彩**自己**的技能。
    我最初写成了 `if (p.team === f.team) continue;`（只吃敌方的光），
    结果对手选测试球（没有任何光技能）时，细线一辈子都是最初的黑色，
    玩家完全看不到"吸收→深紫→微光→爆炸"这条升级链。
    **修法：任何带 `light` 特质的弹道都能被细线吸收，包括晕彩自己的魔弹/激光/光炮。**
    **教训：规格里的括注往往是关键定义（"即……"），不能当补充说明略过。**

33. **技能在"位置夹紧之前"触发，拿到的是穿透位置** ——
    边界处理里原本是「反射 → 调技能 → 夹紧位置」，
    所以技能拿到的坐标是这一帧穿透进墙里的位置（最多差 2 个单位）。
    裁光在那里留下质点，连出来的细线端点就跑到场地外，
    观感上像是"凭空画到墙外"。
    **修法：把 `_onWallTouch` 挪到 `u.x = c.x; u.y = c.y;` 之后**，
    让技能看到的一定是贴到墙面上的坐标。速度覆盖依然有效（技能仍在反弹之后执行）。
    **教训：给技能传位置时，先确认这一刻的位置是不是"最终位置"。**

34. **`onHpBelow` / `onHits` 根本没有分发点 —— 开华永远不会发动** ——
    `_runSkills` 里写好了这两种触发的判定分支，但 `step()` 里从来没有人调用它们。
    于是"血量降到 500 以下就开华"这条规则安安静静地失效了 ——
    不报错、不警告，只是永远不发生。
    **修法：在 `step()` 里补上 `_runSkills(u,'onHpBelow')` 与 `_runSkills(u,'onHits')`。**
    **教训：加了新的触发类型，必须同时确认"谁在什么时机调用它"；
    光有判定分支等于没有。**

35. **永不消失的持续物件会拖垮模拟（细线无限累积）** ——
    裁光的细线不会自然过期，只会在被踩爆时消失。
    一场 5 分钟的对局能撞墙上百次，细线就堆到几百条；
    而每帧都要做「细线 × 小球」的线段距离检测，复杂度 O(线数 × 球数)。
    极端情况（多个晕彩各自留线 + 析光分身也带裁光）实测直接把
    40 秒的对局跑到几分钟都跑不完。
    **修法：给裁光加 per-owner 上限（同时最多 8 条，超出顶掉最早的），
    并在引擎侧留一道全局安全阀 `MAX_FIELDS = 400`。**
    **教训：任何"只增不减"的实体列表都要在设计时就问一句"谁负责回收"。**

36. **"光"加成算错了层级：开华的 +50 和碰撞伤害混在一起** ——
    开华既要给"光"技能 +50，又要给碰撞伤害 +50。
    最初把它们都塞进 `lightBonus`，结果"只装开华"算出 0（基础碰撞）+ 50，
    再被 `_lightDamage` 又叠一次，变成 100 —— 与设定不符。
    **修法：碰撞伤害只认 `unit.melee` 一个数**
    （基础 0 → 折光给 100 → 开华再 +50，两者都有就是 150），
    `lightBonus` 只作用于技能伤害，两者互不叠加。
    **教训：一个数值有两个来源时，先把"谁负责哪一段"写清楚再写代码。**

37. **激光的拖影不能靠"宽度/半径比"去判断** ——
    长条弹道（激光）要沿运动方向画拖影，否则速度 1000 的弹道看起来是一串断点。
    最初用 `宽 > 半径 × 2.4` 来识别，但激光的宽度恰好是半径的 2 倍
    （宽 16 / 半径 8）—— 和普通圆弹完全一样，比值永远区分不出来，
    拖影一次都没画出来。
    **修法：弹道带显式的 `beam` 标记，快照里用 kind 字段的 2 表示光束。**
    **教训：靠"数值范围"去猜类型，遇到重叠区间就会静默失效；
    类型就应该用显式标记表达。**

38. **召唤出来的单位要手动补一次"技能安装"** ——
    被动技能与钩子是在构造函数里统一安装的，而召唤发生在战斗中，
    走不到那条路。结果分身身上虽然有 `skills` 列表，`hooks` 却是 `undefined`，
    一用就崩（`Cannot read properties of undefined (reading 'onHit')`）。
    **修法：抽出 `_initUnitSkills(u)`，构造函数与 `_spawnSummon` 共用。**
    **教训：同一种初始化有两条入口时，就应该只有一个函数。**

39. **`step()` 在对局结束后会立刻返回 —— `while (frame < N) step()` 变成死循环** ——
    诊断脚本里常用"推进到第 N 帧"的写法。但 `step()` 开头就是
    `if (this.over) return;`，对局一旦结束 `frame` 就再也不增长，
    这个循环永远转不完。脚本表现为"没有任何输出、也不退出"。
    **修法：循环条件必须带 `&& !b.over`（`tests/diag/yuncai.mjs` 的 `advance()` 就是这个）。**

40. **stdout 重定向到文件时是带缓冲的，看不到真实进度** ——
    排查"脚本卡在哪一节"时，`console.log` 的分节标题会被攒着一起写出去，
    看起来像是卡在很靠前的位置，实际可能已经跑到很后面。
    **修法：进度标记走 `process.stderr`（无缓冲）。**

### 桃夭的五个技能

> 这一节的坑和晕彩那批不一样：晕彩的问题多在"引擎没提供这个机制"，
> 桃夭的问题多在**"机制已经有了，但边界条件写错了"** ——
> 叠层算不算数、单位对不对得上、默认装配会不会自带冲突。
> 共同点是它们都不会报错，只会**安静地算错**。

41. **速度模型里混用了两种单位 —— 移速变成 120002** ——
    引擎内部位置/速度是定点整数（`SCALE = 1000`），但技能参数、界面显示用的是
    "世界单位"（120 就是 120）。加了陀螺的 `speedBonus` 之后，
    `baseSpeed` 是定点数（120000）而 `speedBonus` 是世界单位（+2），
    两者相加得到 120002 —— 球瞬间飙到十倍速。
    **教训：速度相关的每个字段都要在名字上写明单位**，
    并且只允许 `setSpeed()` / `refreshSpeed()` 两个函数去改，
    边界处统一做一次换算。**同一类数值有两种单位时，混用是迟早的事。**

42. **叠层回调挂在弹道上，于是"没装这个技能"的球也在偷偷叠层** ——
    认真拉矢的 +5 是写在箭矢的 `onHit` 里的。但箭矢是映霞发射的，
    **不管装没装「认真拉矢」都会发射**，于是没装这个技能的桃夭照样在叠层：
    实测满层时箭矢打出了 80 而不是规格里的 50。
    **教训：写在"别的技能产生的实体"上的回调，必须自己确认"本体到底装没装我"。**
    本项目的修法是每个入口都过一次 `hasAim(unit)`。

43. **互斥技能的"默认装配"会自带冲突** ——
    默认装配取技能表的**前 3 个**，而映霞①②是互斥的。
    照①②③④⑤的自然顺序写，默认装出来的桃夭就自带一对互斥技能：
    界面显示装了 3 个、引擎只认 2 个，玩家什么都没做就少一个技能。
    **修法：把「枯」排到技能表第 4 位（顺序即默认配置，是有意的）。**
    另外补了一条**通用不变量**进 smoke：每个球种的默认装配都不允许有互斥冲突 ——
    以后加新角色时会自动被拦下，不用靠记性。

44. **把"每帧接触伤害"也算成"被攻击"，层数一秒顶满** ——
    陀螺是"被攻击时叠层"。裁光的质点/细线是**每帧**结算的（一秒 60 次），
    照字面实现的话，桃夭只要踩进一条细线，10 层上限在一瞬间就满了，
    等于白送满层。场地灼烧同理。
    **修法：只有"真正的打击"（近战碰撞、弹道命中、爆炸）才叠层**，
    每帧持续伤害与区域灼烧不算。这和作者对"每帧 1 点"的原始设定是自洽的：
    那种伤害本来就不该按"次数"计数。

45. **`dmg:` 和 `damage:` 差三个字母，伤害静默变成 NaN** ——
    新写映霞[荣]/[枯]时，参数表里顺手写了 `dmg:`，
    而发射函数读的是 `spec.damage`。JS 不会报错，`undefined` 参与算术得到 `NaN`，
    弹道创建成功、能飞、能命中，只有伤害是 NaN ——
    而 `NaN` 比较永远为 false，所以血条一动不动，看起来像"箭没打中"。
    **教训：这类"字段名拼错"的 bug，类型系统能挡、测试能挡，唯独读代码挡不住。**
    现在的诊断里有一条专门断言箭矢伤害是个**有限正数**（`Number.isFinite`），
    就是为了让这类错误立刻现形，而不是伪装成命中问题。

46. **给渲染层加"前置动作"，就必须先让引擎开口 —— 快照不够用** ——
    做"拉弓"时第一反应是让渲染层自己算：读取技能冷却、倒计时、摆姿势。
    但渲染层**只读快照**（这正是暂停/倍速/回放全部免费的原因），
    而快照里根本没有冷却剩余时间 —— 它无从知道"还有 0.4 秒就要射箭"。
    退一步让它按 `performance.now()` 推算，就等着看**暂停时弓一直拉着不放**吧。
    **修法：把"想看到的东西"继续往快照里加** —— `castP`（施法进度）与
    `aimAngle`（瞄准角）各占一位，快照从 13 位扩到 15 位。
    判断标准很好记：**凡是渲染层"算不出来"的东西，都不该由它算。**
    > 扩快照本身的代价是 0：所有读取方走的是导出的 `SNAP_STRIDE` 常量，
    > 没有一处硬编码 13。加完两位，八套测试一个都没坏。
    > 这也是当初坚持"绝不硬编码步长"的回报。

47. **`face` 是"运动方向"，不是"朝向敌人"，两者差得很远** ——
    快照里早就有 `face`（由 `atan2(vy, vx)` 算的运动方向），
    看到"要一个朝向"很容易直接拿它用。但这个游戏的小球是**匀速直线运动**的：
    `face` 只在撞墙或碰撞之后才变一次，而瞄准要每帧跟着敌人转。
    诊断实测 600 帧里有 **466 帧**两者不同，差距经常超过 90° ——
    拿 `face` 当瞄准角，弓会大部分时间指着空气。
    **教训：字段名像不代表语义像。**
    真正要看的是"这个值是谁、在什么时机、按什么规则算出来的"。

### 缇娜的七个技能

48. **回调传了但没"登记"，弹道会安静地白跑一趟** ——
    蝙蝠要"命中后掉头飞回缇娜、抵达时回血加魔力"，所以发射时传了 `onReturn`。
    实测症状：**11 次命中、0 次返回结算** —— 弹道照常掉头、照常飞回、
    照常抵达，然后在沉默中消失，什么都不会发生。
    原因：`_spawnProjectile` 是**逐字段拷贝**的（`onHit: p.onHit || null` …），
    里面没有 `onReturn` 这一行。
    **教训：往一个"白名单式拷贝"的对象里加新字段，光改调用方不够。**
    这类 bug 没有任何报错，只是"效果没发生"，所以只能靠断言守住
    —— 诊断里那条"蝙蝠会返回缇娜身上"就是为它写的。

49. **引擎和技能抢着收尾，技能永远收不到尾** ——
    吸附到期后要把目标身上的"移速减半"还原。引擎的计时段（phase 1）
    写着 `if (u.latch && frame >= untilFrame) u.latch = null`，
    而技能的 `onThink` 在 phase 2 —— 等技能醒来时 latch 已经是 null，
    那段还原代码**永远不执行**。
    症状：目标被永久打对折（跑完一整局都还是半速）。
    **修法：生命周期只让一个地方负责。** 引擎不再清除，只负责"到期后不再把位置按上去"；
    清除与还原都归设置它的技能。**两个地方都能收尾 = 两个地方都不收尾。**

50. **锚定物体"先摆位置、再积分" = 每帧多走一帧的位移** ——
    光柱的位置每帧从缇娜身上抄，抄完又跟着走了通用的 `p.x += vx*DT`，
    于是每帧多漂 `v × 1/60`。实测光柱离缇娜 **10 个单位**
    （速度 600 单位/秒 × 1/60 秒 = 10，正好对上）。
    这个偏移很小、小到肉眼几乎看不出来，但它是错的，而且**随速度线性放大**。
    **教训：位移积分要看好"这个物体的位置到底是谁说了算"。**
    锚定物体的位置不是积分出来的，就必须跳过积分那一段。

51. **引擎已经发过的事件，技能又发了一遍 —— 每次射击报成两发** ——
    `_spawnProjectile` 自己就会 `emit('shoot')`（带 px/py/color/tag），
    我在技能里为了"顺手"又发了一条。上层统计里 30 发变成 60 发。
    **教训：写新技能前先确认"这件事引擎是不是已经替你做了"。**
    现在 `fireShot` 里留了一行注释专门说明这件事，免得下一个人再加回去。

52. **"先结算伤害、再分发技能"的顺序，会让触发那一下的联动落空** ——
    吸血习性要"每次接触伤害都按数值回血"，做法是挂在引擎的 `onHit` 钩子上。
    但触发吸附的**那一下**伤害发生在 `run()` 之前 ——
    那时 `unit.latch` 还没建立，钩子里的 `if (!unit.latch) return` 直接把它挡掉了。
    实测"3 跳只回了 2 次血"。
    **修法：由 `run()` 补上第一次**（伤害值就是 `_meleeDamage(unit)`，
    因为触发它的正是缇娜的碰撞伤害），之后两跳继续走钩子。
    **顺序是有语义的**：先有伤害才有触发，所以"触发那一下"永远拿不到触发后的状态。

53. **单位换算漏了一处，效果就是"看不见特效"（最难查的一类）** ——
    弹道的 `radius` 是**定点数**（要乘 `SCALE`），而技能参数表里的 `r` 是**世界单位**。
    缇娜的蝙蝠和霰弹都写成了 `radius: P.r`（漏了乘号），于是半径成了 **0.005 世界单位**：
    画面上是一个亚像素点 —— **作者的原话正是"蝙蝠目前看不到特效"** ——
    而且碰撞几乎撞不到（只有圆心完全重合才判中）。
    **这类 bug 不报错、不掉血、日志干净，唯一的症状就是"东西没出现"。**
    特别值得记的是：当时 tina 诊断已经有 83 项、其中还包括"蝙蝠会命中""每次返回回 6 血"，
    **全都通过了** —— 因为圆心重合时确实会命中，返程逻辑也确实跑通了。
    断言测的是"逻辑对不对"，没测"画得出来吗"。
    > **修法不只是补上乘号，而是补一条通用不变量**：遍历所有球种各打一局，
    > 检查每一枚出现过的弹道的 `r / SCALE` 是否落在 1~40 世界单位、`w` 是否落在 0~200。
    > 写漏乘号得到 0.005、乘两次得到 5000，两头都会被抓住。
    > 以后新角色、新技能自动被覆盖，不需要谁记得加断言。
    > （这条不变量是**注入故障验证过的**：把乘号去掉，它报 `缇娜/bat: r=0.005`。）

54. **把"默认值"固化进存档，等于以后改默认对老玩家不生效** ——
    准备界面里 `null` 的语义是"跟随该球种的默认装配"。但 `ensureSpecies` 一读完就把它
    **写成了当时那个具体数组**，于是"跟随默认"变成了"写死成当前默认"。
    这事平时看不出来，直到某个球种的技能表**变了**：

    > 缇娜注册时技能表是空的（为了让球先进场试手感），`defaultSkillsFor('tina')` 返回空数组。
    > 那一格被固化成了 `[]`。两天后补上 7 个技能 —— **老存档里那格还是 `[]`**。
    > 玩家的观感是"缇娜的技能全都没有特效"，实际是她**一个技能都不放**。

    **要命的地方在于它极难往这个方向想**：症状是"看不到特效"，
    于是先怀疑渲染、再怀疑美术 —— 而渲染层其实一切正常
    （我甚至把那一帧的绘制调用全 dump 出来，确认弹道确实被画了）。
    真正的原因是"她压根没发射"。

    **修法两层：**
    - **默认值不进存档**：`null` 一路保持到读取端，由 `equippedOf()` 现算。
      这样以后改默认装配，没被玩家动过的格子会自动跟上。
    - **一次性迁移**（带 `migrations` 标记）：把历史遗留的空装配还原成"跟随默认"。
      标记是必须的 —— 玩家**主动**清空某个球的技能是合法选择（存空数组），
      若无条件还原，就会把玩家的选择反复抹掉。

    > 顺带一条教训：**"默认值要不要写回存储"是一个必须明确回答的设计问题。**
    > 写回去实现最简单（读一次就完事），代价是默认从此冻结在第一次读到的版本上。
    > 只要这份默认值以后可能变，就不能写。

55. **半径漏乘 `SCALE`：逻辑全对，只是"画不出来"** ——
    弹道的 `radius` 是**定点数**（要乘 `SCALE`），技能参数表里的 `r` 是**世界单位**。
    缇娜的蝙蝠和霰弹都写成了 `radius: P.r`，半径成了 **0.005 世界单位**：
    画面上是一个亚像素点（作者原话"看不到特效"），碰撞也几乎撞不到。
    当时 tina 诊断已有 83 项、包含"蝙蝠会命中""每次返回回 6 血"，**全过** ——
    因为圆心重合时确实会命中，返程逻辑也确实是通的。
    **断言测的是"逻辑对不对"，没测"画得出来吗"。**
    -> **修法是一条通用不变量**：遍历所有球种各打一局，检查每一枚弹道的
    `r / SCALE` 是否落在 1~40、`w` 是否落在 0~200。漏乘得 0.005、乘两次得 5000，
    两头都抓；新角色自动覆盖。（用**注入故障**验证过：去掉乘号它报 `缇娜/bat: r=0.005`。）

57. **光柱"碰到细线"不能只看它的锚点** ——
    细线吸光的判定原来是 `点到线段距离(p.x, p.y, 细线) <= f.halfW + p.r`，
    对普通弹道没问题：弹道的位置就是它自己的位置。
    但**锚定光柱的位置是主人的位置** —— 光柱横穿整个场地，
    判定却只看晕彩站在哪儿，于是只有贴着她那条细线才算"碰到"。

    **顺带挖出一个单位 bug**：`f.halfW` 是**世界单位**（0.6），`p.r` 是**定点数**（6000）。
    `f.halfW + p.r` 等于把 0.6 加在 6000 上 —— 细线自身的宽度被完全忽略，
    一直是"弹道圆心压到线上才算"。两项都换算成定点数之后才真的算进线宽。

    这类 bug 的共性是**"同一个量换了个语境，含义就变了"**：
    `p.x / p.y` 对飞行弹道是"它现在在哪"，对锚定光柱是"主人现在在哪"。

58. **测试里手搓的对象会和工厂漂移** ——
    诊断里有几处直接 `battle.projectiles.push({...})` 手工造弹道。
    引擎给弹道加了新字段（`fedLines`）之后，手搓的那份没有，
    于是 `_updateFields` 里读它直接崩 —— **整个诊断一条都跑不下去**。
    这不是"功能坏了"，是"测试里的对象结构过期了"。
    修法不是把字段补齐（下次加字段还会再忘一次），
    而是**让测试走引擎自己的 `_spawnProjectile`** —— 从此不可能漂移。
    > 和之前 `onReturn` 那次是同一个教训的两面：
    > 那次是"工厂漏登记字段"，这次是"测试绕过工厂"。
    > **同一个对象有两份构造代码，早晚会分叉。**

### 诊断方法本身踩过的坑

26. **"每帧覆盖型"状态要专门查"和碰撞/边界的一致性"** ——
    第 25 条那类 bug 的共同点是：某个状态机每帧无条件写一个字段，
    于是物理系统刚算好的结果下一帧就被覆盖掉。
    排查手法：在**每个阶段前后各取一次位置快照**（`tests/diag/dash-wall3.mjs` 就是这么干的），
    一眼就能看出"整帧位置没变"是"压根没被积分"还是"被夹回来了"。
    这类 bug 靠读代码很难看出来，因为每一段代码单独看都是对的。

27. **不要用"猜的数量"当断言，要用物理不变量** ——
    上面第 20 条能藏那么久，是因为早期断言写的是
    "冲刺速度应当在衰减"（采样速度），而不是
    "冲刺期间位移应当 > 100 单位"（采样位置）。
    同理，判断"蓄力时球是不是静止的"必须看**位置有没有变**，
    不能看速度 —— 蓄力中的球被别的球撞到时速度会瞬间非零，
    但下一帧就被状态机清零，它并没有真的移动。
    写断言时先问一句：**这条测的是观感，还是测的我自己以为的实现？**

23. **事件帧相减会天然差 1 帧** ——
    `chargeStart` 打在撞墙那一帧、`dashStart` 打在冲刺第一帧、
    `dashEnd` 打在冲刺结束后的那一帧，直接相减很容易把正确实现误判成差一帧。
    量时长请直接数**状态占用的帧数**（这一帧球处于什么状态），无歧义。

24. **对局结束时最后一段状态是被截断的** ——
    胜负判定后 `step()` 直接返回，若此时球正处于蓄力/冲刺，
    末段帧数会明显偏短（实测出现过一个"只有 2 帧的冲刺段"）。
    统计时长时要把末段排除，并在输出里写明"因对局结束被截断"。

25. **诊断脚本自己维护的"记账状态"会和引擎不同步** ——
    查映霞[荣]的射箭间隔时，判据是"相邻两次单发之间应当差 1 秒"。
    连发那一帧会一次出 5 支，于是我在脚本里加了个 `prevWasBurst` 标记，
    打算"把跨过连发的那一段排除掉"。
    结果断言报出间隔 `1,1,1,1,2,1,...` —— 看着像引擎多发了一轮，
    实际是**我自己的标记没跟上**（连发那一帧记了 true，下一帧就被覆盖成 false）。
    折腾了两轮去查引擎，最后直接把真实帧序列打出来才看清：
    引擎完全正确（`1,1,1,1,1,5,1,1,...`，连发正好在第 6 次），错的是断言。
    **修法：断言不要依赖自己维护的状态机，改成"直接找相邻两次单发来配对"** ——
    判据从"我记得上一帧发生了什么"变成"数据本身长什么样"。
    **写测试时，脚本自己的状态也是一份需要被怀疑的实现。**

26. **"事件帧号"和"快照下标"差 1 —— 同一个坑第二次踩，这次是写新诊断** ——
    查拉弓时序时断言"射出那一帧 castP 必须 = 1"，结果读出 **0.958**，
    而"射出的下一帧"读到 **1** —— 整体平移了一帧，看起来像引擎的时序算错了。
    差点就去改引擎。实际原因是引擎里的顺序：

    ```
    step() 开头 this.frame 还是 F
      → 技能在这一步中途发动，_emit 记下 f = F
      → 这一步最后 this.frame++ 变成 F+1，然后 _record()
    ```

    所以"这次射击造成的状态"落在 `snapshots[F + 1]`，而 `snapshots[F]` 是**上一步**的。
    诊断里必须 `e.f + 1`。
    **这个坑 README 第 23 条早就记过了**（"事件帧相减会天然差 1 帧"），
    我还是踩了 —— 因为第 23 条讲的是"量时长"，而这次是"取状态"，我当时觉得是两回事。
    **修法：在诊断里定义一个有名字的换算函数 `snapOf(e) = e.f + 1` 并写清理由**，
    让后面每个人都只有一处需要看，而不是每处各自 ±1。

27. **"诊断写完了却没跑"——构造函数留下的那一帧骗过了搜索** ——
    验证"弓不受陀螺自转影响"时，要先找一帧"拉弓中且陀螺在转"。
    搜索一直返回"没找到"，我却去怀疑陀螺没叠起来。
    真实原因：`new Battle(...)` 之后**只调用了构造函数**，
    而构造函数末尾会 `_record()` 一次 —— 于是 `snapshots` 长度是 1，
    搜索第一步就 `break` 了。**忘了 `runToEnd()`。**
    **教训：这条断言不是"失败"，是"什么都没测到"就报了失败。**
    两者的区别很重要 —— 现在这类"找不到样本"的断言都会把
    "我搜了什么、搜了多少帧"打进详情里，一眼能看出是没测到还是真失败。

### 美术 / 技能 / 玩家操控踩过的坑（近几轮）

28. **资源方向要按"这张图自己的几何"判，不能套用别的图的判据** ——
    能量弹和箭矢能用"重的一头是头"（质量判据），因为亮核 / 箭镞比尾迹 / 箭羽重。
    但**弓不能用质量判**：弦几乎没有重量，重心完全被弓臂和花朵带跑。
    弓要判的是几何 —— 弦是又细又直的线、弓臂是粗的那一坨，**弓臂朝哪边鼓，箭就往哪边飞**。
    光靠一个信号也会错（拉弓帧里那支搭好的箭会混进"细的那一组"），
    所以用两个独立信号投票、**不一致就报错让人看图，绝不猜**。
    **教训：给每类资源想清楚"它凭什么算朝前"，别把上一类资源的判据照搬。**

29. **"两帧方向不一致"是最隐蔽的一类美术问题** ——
    作者给的「映霞[枯]」两张图，**平时那张是镜像的**（弦在右、弓臂朝左），
    拉弓那张是正的。单看任何一张都不觉得有问题，一放进游戏就是：
    球举着弓时是反的，一**拉弓整把弓还会左右翻个个儿**。
    它不报任何错，画面上只是"有点怪"，靠人眼盯很容易漏。
    修法：构建时把每一帧各自摆正（**镜像，不是转 180°** —— 弓上下有别，
    转 180° 会把弓梢和握把也翻掉），并且断言"同一把弓的两帧朝向必须一致"。
    **教训：多帧美术要按"帧之间的关系"验，不能只验单帧。**

30. **改了一半的重构比没改更危险：`balls.js` 改了、`render.js` 没跟上** ——
    把弓的美术从"单一写法"改成"`kindArt` + `arts[]`"时，
    `balls.js` 先改好了，`render.js` 的 `_bow()` 和 `preloadStickers()`
    还在读旧的 `bow.anchor / bow.bowH`。结果是：
    `anchor` 是 `undefined` → 变换矩阵算出 `NaN` → 弓**整个不画**，
    而且不报任何错（canvas 对 NaN 变换是静默忽略）。
    更糟的是当时的"验收"是跑单元测试 —— 它们全绿，因为它们根本没碰渲染层。
    （连 `tools/preview-bow.mjs` 也跟着崩了：它读的也是旧结构。）
    **教训：改数据结构时，先把"谁读这个结构"全列出来再动手**；
    这次的守护是 `art-proj.mjs`：遍历所有球种跑真实对局，
    凡是配置里挂了贴图的弹道，都必须真的在画布上被 `drawImage` 出来。

31. **画布类工具要防"坐标混用"** ——
    ① 把"格子内部的坐标"和"拼到总图上的坐标"混用：所有格子的图都往总图左上角那一格上贴，
    结果**只有第一格有图**，其余全空 —— 看起来像"图没加载"。
    ② 用绝对坐标去画一张只有格子大小的 SVG 覆盖层 → 圆被画到画布外，静默不显示。
    两次都发生在同一个 `preview-proj.mjs` 里。
    **教训：凡"偏移量"一律显式分成 local / global 两套命名**（`lx/ly` 与 `ox/oy`），
    别让同一个 `cx/cy` 既当局部又当全局。

32. **"数出 6 支箭"——快照里混着上一轮还在飞的弹道** ——
    想验"画出来的扇形和真正飞出去的箭逐根对齐"，第一版直接取五连发那一帧
    **所有**带贴图的弹道，数出 6 支、角度也被带偏，看着像引擎多发了一支。
    实际是上一轮单发的那支还在飞。
    修法：用**相对新鲜度**筛"这一批刚出膛的"（`lifeT` 与全场最大值相差 < 2%），
    而不是写死一个绝对阈值（第一版写了 `> 0.99`，而这批的实际值是 0.9896 → 一支都没筛出来）。
    **教训：从快照里取样本时，先问"这一帧里还有谁是同类的、但不是我想要的那一批"。**

33. **同一个公式抄成两份，迟早会漂** ——
    五连发的扇形角度，`skills.js` 里写一份（真正决定弹道）、
    渲染层里又抄一份（决定画出来的扇形）。抄的时候把
    `(k/(n-1))*2-1` 写成了 `((k+1)/(n+1))*2-1`，
    于是**画出来是 14.4°，实际飞出去是 24.06°** —— 差了整整一倍，
    而"预告弹道"正是画这个扇形的全部意义。
    修法：公式提成 `render.js` 导出的 `burstOffsetsDeg()`，渲染层、预览脚本、
    诊断三处共用；诊断再去比**真实弹道的速度方向**（不是配置数字），
    现在最大偏差 0.004°。
    **教训：断言要比"两个独立算出来的可观测量"，不要比"两个抄来的配置数字"。**

34. **"默认值"在枚举里不是中立的：`castKind` 归 0 = 举错武器** ——
    加了"多套弓"之后，`castKind` 从"这一发是不是五连发"变成了
    "这个单位现在该用哪套弓"。而引擎在**没在拉弓**时把它归 0 ——
    0 在新表里是「映霞[荣]」，于是只装「映霞[枯]」的桃夭平时举着荣那把粉弓，
    只有拉弓那 2 秒才变回花枝弓（一场战斗里武器一闪一闪地换）。
    更刁的是构造函数末尾那次 `_record()`：那一帧还没跑过 `step()`，
    整局 362 帧里**恰好第 1 帧**是错的 —— 开战瞬间闪一下粉弓，之后一直正常。
    修法：平时也问一遍技能的 `castKind()`（见 `core.js` 的 `idleCastKind()`），
    构造函数记第一帧前补一次；断言改成**逐帧**看"这一局整局都必须是哪一套"。
    **教训：枚举字段扩容时，先问"旧的那个 0 现在代表什么"；
    还有，"绝大多数帧是对的"不等于对 —— 第一帧也是玩家会看到的帧。**

35. **预览图的背景必须是游戏里的背景，否则比不上** ——
    两张预览（`preview-bow` / `preview-proj`）一开始都用了深色底，
    因为"深色底上发光效果好看"。但游戏场地是**浅色方格纸 `#fdfcf7`** ——
    同一种半透明光晕，在白纸上会淡到几乎看不见。拿深色底去调颜色，
    等于对着错的参照系做审美判断，改完一进游戏全不对。
    顺带一提，这条也是被逼出来的：加"光晕要用**中等饱和度**颜色"这条要求时，
    才发现预览底色和游戏底色根本不是一回事。
    **教训：预览的作用是"替你看一眼真实效果"，那它就必须复刻真实的材质与底色；
    底色选得"好看"而不是"真实"，预览就从证据变成了误导。**

36. **断言要按"这一帧里还有谁"筛样本** ——
    给贴图弹道加光晕与呼吸后，诊断里出现了两类"看着像引擎错了"的假失败：
    ① 一帧里同时飞着蝙蝠和霰弹，却拿**先画的那个椭圆**去比后者的尺寸 → 报"霰弹的光晕尺寸不对"；
    ② 统计蝙蝠的透明度区间时，把**寿命末尾正在整体淡出**的那几帧也算进去 →
    量到 0.000，报"浮动越界"（实际是 0.250~0.400 正好）。
    修法：前者按调用序列归属（从这枚弹道的 `drawImage` 往前找，到上一次
    `drawImage` 为止的那一段就是它自己的光晕）；后者先按 `lifeT ≥ 0.3` 筛掉淡出中的，
    再取同帧里**最亮**的那一枚（同种弹道呼吸相位相同、淡出程度不同）。
    **教训：同一帧、同一种东西往往有好几个，取样本前先想清楚"我要的是哪一个"。**

37. **"默认参数"就是一处隐藏的上限：`normalizeSkills` 不传第三个参数 = 3** ——
    作者报"勾了无限火力也不能真的带 3 个以上"。复现出来的现象很怪：
    点第 4 个技能 → **存档里确实进了 4 个**，但面板重绘后又只勾回 3 个，
    而且再怎么点都长不到第 5 个（每次都从被截断的 3 个重建）。
    根因：`normalizeSkills(speciesId, wanted, maxSkills = MAX_SKILLS_PER_UNIT)`
    的第三个参数是上限，而界面里**三处**调用都忘了传 ——
    `equippedOf()`（面板勾选、汇总统计、下一次点击的起点都读它）、
    `ensureSpecies()`（读存档时整理）、以及早先就改对的 `makeConfig()`。
    少传的那两处不报错、也不影响引擎，只是把面板上的勾选**悄悄截断**。
    **教训一：给函数加"默认上限"时，默认值就是一处隐藏的配置 ——
    开新功能（无限火力）时必须把所有调用点找全，别只改"看起来相关"的那一处。**
    **教训二：测试只走了一条路就等于没测。** 我当初的断言点的是「全部」按钮
    （一次把整份装配写进存档），所以它测不出"逐个点"那条路上的截断 ——
    而作者实际就是逐个点的。现在 smoke 里补的是**逐个勾选**的回归：
    每点一个都核对"面板个数 = 存档个数"，最后再核"引擎建出来的单位是不是 7 个技能"。

38. **改了数值之后，"旧规则的断言"会变成假失败** ——
    作者用素材编辑器把几枚弹道的图相对判定中心挪开了（这正是那个功能的意义），
    于是 `bow.mjs` / `art-proj.mjs` 里"图必须正好居中在判定中心"的断言立刻变红。
    那不是代码坏了，是**规则变了**：新规则是"图的中心落在判定中心 + 配置的偏移"，
    偏移为 0 时等价于旧的居中。两条断言都改成了带上偏移的版本（比原来更强）。
    **教训：加一个"可调项"时，顺手搜一遍所有断言里有没有把旧行为写死的 ——
    否则第一次用它就会看到一片红，还得现场判断哪条是真坏了。**

39. **`hidden` 属性靠的是"默认样式"，任何一条 `display` 都能把它压过去** ——
    我加「战前抽技能」时写了 `.lottery-layer { position:absolute; inset:0; display:flex;
    background: rgba(253,252,247,.9); backdrop-filter: blur(1.5px) }`，
    显隐靠 JS 设 `layer.hidden = true/false`。
    结果 `hidden = true` **完全没用** —— `[hidden]{display:none}` 是浏览器**默认样式**，
    而作者样式里任意一条 `display` 的优先级都比默认样式高。
    于是那块"90% 白纱 + 背景模糊"的层**一直盖在战斗画面上**：
    球、血条、伤害数字全被罩成半透明，整个画面发白又发糊。
    作者报的是"整个画面都模糊了，怀疑领域展开出问题了" ——
    领域其实清白（虽然顺手查出它另一个 bug，见第 40 条），真凶是这块纱。
    **修法两层**：① 全局加一条 `[hidden] { display: none !important; }` 把这个陷阱堵死；
    ② 抽签层改成靠 `.show` 类显隐（默认 `display:none`），不再依赖 `hidden` 属性。
    **教训一：用 `hidden` 属性控制显隐时，那个元素上就不能有作者写的 `display`。**
    **教训二（更疼）：一个"半透明 + 模糊"的遮罩层，症状看起来像渲染坏了 ——
    它会让你顺着"画面怎么变糊了"去查渲染管线，而真凶是一层你没注意到的 DOM。
    排查时的抓手是：**把画面的异常区域裁出来放大**，看清是"整体降透明度"还是"某个元素画错了" ——
    一看就发现连血条和文字都淡了，那不可能是渲染层的问题（渲染层不会统一降低所有东西的不透明度）。**

40. **召唤出来的分身漏拷 `domain`，于是它把自己的被动变成了"关掉全场极光"** ——
    排查上面那个"画面发白"时顺手发现的：作者那局晕彩带了「辉光领域」+「析光」。
    领域是**常驻被动**，`passive()` 里写 `battle.auroraStyle = unit.domain || null`；
    而析光的分身**继承本体的技能**（所以也带领域），它的被动会再跑一遍 ——
    但 `_spawnSummon()` 构造分身时**漏拷了 `domain` 字段** →
    分身的 `unit.domain` 是 undefined → `auroraStyle` 被覆盖成 `null` →
    渲染层 `if (!cfg || !cfg.src) return` → **整场极光当场消失**，
    同时 `auroraAt` 被改成"现在"，气浪还会从分身那一侧重放一次。
    修法两处：`_spawnSummon` 补上 `domain: stats.domain || owner.domain || null`；
    领域的被动只在**第一次**激活时写那三个静态量（`if (!battle.aurora) {…}`），
    并且 `auroraStyle` 只补空、不覆盖。
    **教训：分身漏拷外观字段通常只是"长得不一样"，但漏拷这种"会被被动写进 battle 的状态"
    就会影响**别人的画面** —— 给单位加字段时，`_spawnSummon` 那份构造清单要一起看。**
    守护：`domain.mjs` 的【1.5】节（分身带领域配置 / 领域层不被覆盖 / 气浪不重放）。

41. **预览图的裁剪范围小于特效的最大半径 → 看起来像"特效提前结束了"** ——
    做开华爆发预览时格子只给了 280px（`PX = 4.6`，也就是只看得见 30 世界单位半径），
    而 `bloomBurstSpec()` 的最外环最大到 `12 + 2*9 + 58 = 88` 单位。
    于是后三格的光环**已经扩到画布外面**，图上只剩一颗球 ——
    看上去像"爆发到 44% 就没了"，实际上它还在，只是被裁掉了。
    这种"假象"最危险的地方是：它和"真的提前结束"在图上长得一模一样，
    而我当时正拿它当"特效够不够显眼"的判据。
    **修法**：格子大小从最外环半径反推（`PX = (CELL/2 - PAD) / 92`），
    并在每格标注**那一帧的最外环半径**，让"扩出去"变成可核对的数据。
    **教训：预览图的视野也是一个参数 —— 画之前先问"这个特效最大能到多大"，
    再从最大值反推视野；标注上绝对数值，图就不会骗人。**

42. **编辑器里那几个旋钮是空白的：手写的"取值清单"没人记得更新** ——
    加开华那批常量时，`asset-schema.js` 里登记了 9 个新字段，但
    `ui-assets.js` 读"现值"走的是一份**手写清单** `GLOBAL_VALUES`
    （只列了 PROJ_* 那几个），于是新字段取到 `undefined` →
    数字框显示空白、滑条停在中间。**页面不报错**，作者只会以为"这些参数是空的"。
    修法不是"把 9 个名字补进清单"，而是**把清单删掉**：
    `import * as RENDER from './render.js'` 之后按导出名取（`RENDER[key]`），
    字段的 key 本来就是导出名，以后加常量不必再动这个文件。
    另外在 `check-asset-schema.mjs` 里补了一条守卫：
    **凡是 file 为 render 的字段，那个导出名必须真的存在**（26 个字段逐个核）。
    **教训：一处"需要人工同步的清单"就是一个迟早会漏的地方 ——
    能改成"按名字取"就别维护清单；必须维护的，就写一条自检盯着它。**

    顺带一个纯手误：注释里写 `BLOOM_*/SHAKE_*` 时，
    中间那个 `*/` **把块注释提前结束了**，后面的中文成了代码 →
    `SyntaxError: Invalid or unexpected token`。写注释时避开 `*/` 这两个字符。

43. **我的断言比实现更严格，于是它自己红了** ——
    `dmg-text.mjs` 里核对"红字的字号 = DMG_FONT_PX × (1 + 增益 × 权重)"时，
    一开始按浮点数比（容差 1e-6），而字号写进 `font` 字符串时是 `toFixed(1)`：
    22.1088 被写成 22.1，差 0.0088 > 1e-6 → 393 个"异常"。
    代码没错，是**断言拿未取整的值去比已经取整的字符串**。
    容差改成最后一位的一半（0.05）。
    **教训：比"打印出来的值"时，容差要按打印精度给；
    不然测出来的"失败"全是自己的格式问题（前面第 38 条也是同一类假失败）。**

44. **`.bat` 用 LF 行尾：cmd 会执行一半、还给你一堆莫名其妙的报错** ——
    写启动器时文件内容、逻辑都对（单独把那条 PowerShell 拿去跑是好的），
    可双击之后输出是这样：
    ```
    '面（服务器顺延到' 不是内部或外部命令，也不是可运行的程序
    '5173' 不是内部或外部命令
    '素材编辑器」两个按钮。' 不是内部或外部命令
    ```
    而且它**照样打印了提示、还 pause 了** —— 看起来像"分支判断写错了"。
    真正的原因只有一个：**文件是 LF 行尾**。cmd.exe 逐行读取批处理，
    LF-only 时它对 `if (...)` 这类**括号代码块**的解析会错乱，
    把块里的中文行当成命令去执行。
    修法：整个文件转成 **CRLF**（UTF-8 无 BOM + 第二行 `chcp 65001`）。
    修完同样的双击立刻正常，`netstat` 也看到服务器起来了。
    **教训：`.bat` / `.cmd` 的行尾是**语义**的一部分，不是风格问题 ——
    所以 `tests/diag/launcher.mjs` 现在会数每个 `.bat` 的 CRLF/裸 LF 数量
    （裸 LF 必须为 0），并顺手写了一份 `.gitattributes`（`*.bat text eol=crlf`）
    免得以后真用 git 克隆时被自动转成 LF，又踩一次。**
    顺带一条：这类"文本文件的编码/行尾"问题，**光看内容永远看不出来**，
    跑一次才是唯一可靠的验证方式（`cmd /c "启动器.bat < nul"`）。

45. **锚点里带上了"会被改的那个值"：写回成功，校验却报"锚点找不到"** ——
    做数值编辑器时，我给魔弹的光柱伤害挑了锚点 `laserDmg: 150,`
    （想着"这两处 laserDmg 靠值区分，够具体了"）。结果自检里出现很怪的一行：
    **定位成功、现值 150，但紧接着"试写"失败：锚点找不到**。
    原因是定位与校验都用同一个字段描述：
    ① 第一次定位：在**原文件**里找到了 `laserDmg: 150,` ✓；
    ② 写回：值变成 `160`，于是源码里**再也没有** `laserDmg: 150,` 这个字符串；
    ③ 往返校验要在**写回后的文本**里再定位一次 → 锚点消失 → 报错。
    换句话说：**锚点必须是不随这次改动而变的东西**。
    修法：锚点换成上面那行注释里的唯一一句话（`/* 光效环绕的颜色（画在贴图下面…`），
    同样的坑 `tickPerSec: 3,` 也踩了一次，一起换成 `p3: {`（键名，不含值）。
    **教训：写"定位规则"时先问一句"这个字符串在我改完之后还在吗"。
    凡是含被改值的锚点，都是给自己埋一颗定时炸弹 —— 第一次改就炸。**
    守护：`check-asset-schema.mjs` 的"往返一致"就是专门抓这个的。

46. **值的扫描只认逗号：行内对象的最后一个值被读成 `0.15 }`** ——
    `domain: { dodge: 0.10, dodgeBloomed: 0.15 },` 这种**写在一行里**的对象，
    最后一个值后面跟着的是 `}` 而不是 `,`。原来的扫描只认 `,` `;` 换行，
    于是读出来的"现值"是 `0.15 }` → `Number()` → `NaN` →
    写回直接报"不是有限数：NaN"。
    修法：结束符补上 `}` 与 `)`（行内对象/调用都是靠括号收尾的）。
    **教训：解析"人手写的源码"时，别只想着最常见的那一种写法 ——
    同一个文件里既有跨行对象也有行内对象。**
    另外数组值是同一类问题的另一种写法：`dmgByStage: [1, 2]` 里的逗号
    也不是值的结束，得按配对 `[` `]` 扫（这个在加 `nums` 类型时顺手补上了）。

47. **正在跑的服务器是"启动那一刻的代码"：加了新类型，保存直接 409** ——    数值编辑器给 `formatValue` 加了 `nums`（数字数组）类型，
    自检全绿；可是用**真实服务器**保存时，请求被 409 挡下：
    `字段 cgDmg 改不动：不认识的字段类型：nums`。
    原因：`tools/serve.mjs` 在启动时 `import` 了写回实现，
    而它是个长驻进程 —— 我给的那份新代码它根本没见过。
    （字段清单一早就是"每次保存重新读"，写回实现却漏了，于是只有它落后。）
    修法：写回实现也改成**每次请求带时间戳动态 import**，
    以后改写回逻辑同样不用重启服务器。
    顺便验证了一件好事：**失败时一个字节都没写**（整份请求全有或全无）。
    **教训：长驻进程里"启动时 import 一次"的东西，都是"改了不生效"的候选人；
    要配一个"改完必须重启"的提示，或者干脆每次重新读。**

48. **"速度 0"挡不住碰撞：木桩被打得满地跑** ——
    做木桩时第一版只写了 `speed: 0`，自以为"它不会动"。实际跑起来是这样：
    它确实不会**自己**走（巡敌/转向都是按 `speed` 给速度的），
    但对手撞上来的一瞬间，弹性碰撞的冲量照样把它推出去 ——
    而"被撞就飞"的靶子根本没法用来演示技能。
    翻引擎才看清有几条**绕开 speed 直接改 `vx/vy`** 的通道：
    碰撞冲量、重叠时的分离推挤、弹道击退、撞墙反弹、分离速度下限。
    修法是两层：
      ① 数据上给木桩 `immovable: true`，引擎把它按**质量极大**处理
         （`1e9` 而不是 `Infinity`：两个木桩重叠时 `Infinity/Infinity` 会算出
         `NaN` 把位置毁掉），于是冲量与推挤全转嫁给对方，撞上来的一方自己弹开；
      ② 每帧积分**之前**再清一次它的速度，兜住那些不查质量的通道
         （击退、冲刺、反弹、分离下限）。
    直觉上"速度为 0"和"推不动"是同一件事，其实是两个机制。
    **教训：写"它不会动"这类断言时，要把它放在**真会被撞**的场景里跑一整局
    （`dummy.mjs` 就是让三颗球围着它撞满一整场，再断言"位置一个定点单位都没变"）。
    顺带一个发现：`_ensureMoving`（当年为了"别让球停住"加的补丁）
    会把静止的球**主动推起来** —— 对木桩是反效果，所以它必须显式豁免。

49. **定点数与世界单位混着比：长剑"谁都够不着"** ——
    见晴②的扇形判定里我写的是
    `if (dist > unit.r + unit.swordLen + targetR) return 0;`
    看着没问题，实际**一个敌人都砍不到**。
    原因是 `unit.r` 与坐标都是**定点数**（×1000），而 `swordLen` 是**世界单位**：
    左边是 40000（40 单位 ×1000），右边是 16000+32+30 = 16062 —— 于是"够不着"。
    反过来（如果 swordLen 写成定点）就会变成"全屏都能砍到"，更危险。
    修法：在判定函数里**统一换算到世界单位**再比（`dist / SCALE`、`unit.r / SCALE`），
    并把这条写进注释 —— 这个项目里两种单位长期共存，
    凡是"半径 / 距离 / 长度"放进同一个式子的地方都得先问一句"这三个数同单位吗"。
    **教训：定点数混单位不会报错，只会让判定悄悄失效；
    出现"条件明明满足却进不去"时，先把式子两边的量纲写出来。**

50. **两个累加器共用一个字段：切回淡绿之后护盾一点都不掉** ——
    ① 的淡粉每秒 +30、非淡粉每秒 −5，两者都用 `unit.flags.shieldAcc` 攒余数。
    而"淡绿分支"里有一句 `shieldAcc = 0`（本意是清掉加盾的余数），
    结果把**衰减的余数也一起清零** → 每帧都从 0 开始减 0.083，永远到不了 1 →
    护盾永不衰减。表现是"作者看到的：切走之后护盾一直是满的"。
    修法：加盾与衰减各用一个累加器（`shieldAcc` / `shieldDecayAcc`）。
    **教训：一个"攒够 1 点再结算"的累加器只能服务一件事。
    两件事共用时，任何一边的"清零"都会把另一边一起抹掉 ——
    而且这种 bug 只在"两个方向来回切"时才显形，单向测试永远测不出来。**

51. **"状态设一次"被后面的绘制改回来：起飞看起来完全不透明** ——
    起飞要做三件事：虚化、变大、加影子。我在单位绘制块的开头设了
    `ctx.globalAlpha = FLY_ALPHA`，但后面几段装饰（队伍色环、水镜圈、护盾、长剑）
    各自会把 `globalAlpha` 改回 1 —— 等轮到画球体时，透明度已经是 1 了。
    只有装了水镜的见晴碰巧没这个问题（水镜那段的结尾会把 alpha 设回 `FLY_ALPHA`），
    所以"单独测飞行的见晴"才会露馅。
    修法：在**画球体之前**再设一次 `if (flying) ctx.globalAlpha = FLY_ALPHA;`，
    并且加上注释说明"会被后面的装饰改掉"。
    **教训：canvas 的 globalAlpha / fillStyle 是全局可变状态，
    "在块首设置一次"这种写法只要中间夹了别的绘制就不可靠。
    要就"紧挨着使用处设置"，要不就 save/restore 包起来。**

52. **我的断言信号选错了：拿"掉血"去验证挥剑** ——
    ② 的用例原本断言"敌人掉了 80 血"，结果一直红。查下去发现
    打中它的其实是**碰撞伤害**（30 点），而挥剑要么没触发、要么和碰撞混在一起；
    ④ 的"每帧吃 5 点"也因为同时有碰撞伤害而量成了 35。
    修法：改成看**事件**（`swordSwing` 的 value 就是那一下的伤害）、
    或者先把干扰源关掉（把对方的 melee 清零、把两球摆到不重叠的距离）。
    另外还踩了两个纯测试自己的坑：
      · 循环变量名 `c` 被箭头函数参数 `c` 遮住，`c.color` 变成 undefined → 4 条断言永久假红；
      · 面板断言取了 `text`，而"攒满要 10 秒"那句在 `note` 里。
    **教训：断言要盯"最接近事实的那个信号"。**
    "掉血多少"是多个机制叠加后的结果，拿它反推某一个机制非常容易误判；
    事件流里的 value 才是那个机制自己报的数。

53. **累计量的触发条件：不清零就等于"永远成立"** ——
    ④ 起飞的触发是"累计移动 1560 单位"。第一版只有"飞行中不计距离"，
    没在起飞那一刻把计数器清零 —— 于是落地当帧累计量还是 ≥ 1560，
    条件立刻再次成立 → **她一直飞在天上**（作者实测报的就是这个）。
    修法：起飞时 `traveled = 0`；飞行中本来就不累计（那一段位移是"飞"的，不是"走"的）。
    验证也补成了完整的一轮：起飞清零 → 飞行中保持 0 → 落地 2 秒内不再起飞 →
    再走满 1560 才第二次起飞。
    **教训：凡是"累计到某个值就触发"的条件，都要问一句"触发之后这个量怎么办"。
    三选一：清零（每次都要重新攒）、保留（那就得靠别的条件挡住重复触发）、
    或者设一个"下次触发的门槛"（`next = 当前 + 步长`）。
    忘了选，默认就是"每帧都触发"。**

54. **作者改了几个数值，我的"定宽窗口"就定位不到了** ——
    素材编辑器的字段定位规则是"唯一锚点 + 窗口内找键"。
    见晴②那一段的窗口原本写的是 `window: 400`（从段首注释往后数 400 个字符）——
    刚好够到最后一个字段 `purgeMax`。作者把 `defInterval: 5` 改成 `2.5`，
    **多出两个字符**，`purgeMax` 就掉到窗口外面了，自检立刻红：
    「锚点之后没找到键 purgeMax（窗口 400 字符）」。
    这不是他的错，是**窗口宽度天生怕"文本变长"**：注释多一句、数字多一位、
    行内注释换个说法，都可能把最后一个字段挤出去。
    修法：给每个字段加 `stop` —— 窗口的硬边界就是**下一段的段首注释**
    （`stop: '/* ③ 水镜·魔力共鸣（深蓝紫色和白色） */'`），
    这样"这一段里的字段"永远定位得到，作者随便调数值都不会影响定位。
    **教训：凡是用"往后数 N 个字符"来圈范围的规则，都要配一个语义边界（stop）。
    数值前缀写死宽度，等于把"改内容"和"改定位"绑在了一起。**
    顺带一条同源的经验：这一轮之后，见晴的诊断也改成"只钉机制、不钉数值"——
    **作者调数值不该让测试变红，只有机制坏了才该红。**

55. **`overlapping()` 只挡住了碰撞，没挡住碰撞伤害** ——
    见晴起飞时"只与墙壁发生碰撞"，我在 `overlapping()` 里加了一句
    `if (phasing) return false`，以为冲量、分离、撞伤三件事都归它管 ——
    结果帧伤测试一直比预期多 60 点/秒。
    查下去发现：**碰撞伤害走的是另一条路**。
    `_collide()`（冲量 + 位置分离）用 `overlapping`，
    而 `_resolveAttacks()`（接触伤害结算）**自建了一套网格**，
    只算距离、从来不问 `overlapping` —— 于是她一边"穿透"飞过去，
    一边每 0.5 秒照样挨一下对方 30 点的碰撞伤害（30 ÷ 30 帧 = 每秒正好多 1 点/帧）。
    修法：在 `_attackPair()` 开头补一道 `phasing` 守卫。
    **教训：一个判据（"这两球算不算接触"）在引擎里有两处实现，
    加规则时只改一处就等于没改。** 定位手法值得记：
    **"多出来的伤害恰好是每秒 1 点"这种整齐的差值，几乎都是"某个固定伤害 ÷ 冷却"** ——
    顺着它反推（30 ÷ 0.5 秒）就能找到那条漏掉的路径。

56. **"每秒最多转 45°"写成技能里的一句旋转，实测是 75°/秒** ——
    ④ 的追踪我在技能 `onMove` 里写了一句 `_deflectTowardEnemy(unit, 45 * DT)`，
    看着完全对得上"每秒最多 45°"，一测却是 75°/秒。
    原因是**转向来源不止一处**：引擎在主循环里先跑一遍全局微转向
    （详细设置里的「持续微转向」，默认 **30°/秒**），技能的追踪是在那之后
    的 `onMove` 里**再**转一次 —— 叠加 30 + 45 = 75。
    这类"上限"型需求不能靠"我只转这么多"来保证：只要还有第二个人也在转，
    写死在自己这一层的角度就没有意义。修法是把它做成**引擎的统一裁决**：
    单位登记 `turnCapDegPerSec`，引擎在 `onMove` 之后、积分之前，
    把本帧航向钳在"本帧开始航向 ± 上限×DT"之内。
    两个细节：① 基准航向必须在**所有**转向之前记录（不然钳的是"半截"航向）；
    ② 钳制要放在**积分与撞墙之前** —— 撞墙那个"瞬间指向敌人"是作者明确要的，
    不该被 45°/秒 拖住。
    诊断里补了一条回归：把详细设置的微转向开到 60°/秒，总量仍须 ≤ 45°/秒。
    **教训：凡是"最多/至少"这类总量上限，先问一句"还有谁会改这个量"。**

57. **"发动了"和"生效了"是两件事：偷来的技能只有一半在跑** ——
    作者报的 bug：「缇娜通过蝙蝠发动见晴的变色能力时，并没有触发对应效果」。
    查下去发现代码**一行都没错**：`stealAndCast` 老老实实调了
    `sk.run({battle, unit: tina, target})`，见晴 ① 的 `run()`
    也确实执行了 —— 它把颜色位写成 1 或 2，连画面上的水镜圈都真的变了色。
    但**那类能力的完整效果不在 `run()` 里**：
    淡绿每秒回血、淡粉每秒涨护盾、护盾挡伤害，全都写在
    `hooks.onMove` / `hooks.onBeforeDamage` 里 —— 而钩子是**建单位时按
    `unit.skills` 登记的**，缇娜身上根本没有这些钩子。
    所以它"发动成功、效果为零"，事件流里连一条报错都没有。
    教训有两条：
    · **给一个技能分类时，"有没有 run"只是"它能不能被放一次"，
      不等于"它放一次就完事"。** 效果是持续状态的能力要标出来
      （现在用 `sustain: true`），并按"临时装到使用者身上 N 秒"处理；
    · **验证"某个能力生效了"要盯那个能力的实际产物**（回血 / 护盾 / 伤害），
      不能盯"它有没有被调用"。这次要是只断言 `steal` 事件存在，
      bug 会被测试原样放进仓库。

58. **"借来的东西"必须由引擎收回，而且只能收回自己那一份** ——
    接着上一条做"借用 5 秒"时，两个坑都是同一类：
    · 归还时**不能整个清空** `unit.hooks` —— 缇娜自己也有钩子（霰弹的
      `onThink` 之类），一把清掉会连带把本体的技能打死。要**按函数引用**
      一个个摘（装载时记下 [钩子名, 函数] 的清单）；
    · 归还时**不能只摘钩子**：被动留下的东西（移速 +10、那柄剑、水镜颜色、
      被换掉的资源条）得由技能自己的 `onUnborrow` 收尾。而且不能交给
      "借出方"去收 —— 见晴可能早就阵亡了（和"限时移速倍率必须由引擎还原"
      是同一个道理）。
    另外"重复借同一个技能"要**只续时长、不重跑被动**，否则移速 +10 会叠成 +20。

59. **实时操控里"播放头到末尾"是常态，用它当"打完了"会自己按暂停** ——
    播放循环原来是这么判结束的：`if (ui.frame >= totalFrames) { ui.playing = false; }`。
    这在"一次性算完整局"的模型里完全正确 —— 播放头追上了预算出来的总帧数就是放完了。
    但玩家操控改成**实时推进**之后，播放头**每帧都等于**当前总帧数，
    于是第一批帧一跑完就立刻 `playing = false`。
    表现极具误导性：**WASD 按了球不动、技能键也没反应**（引擎一步都没走），
    但技能栏、血条、战报都正常显示（那些是开局那一下就画好的）——
    看着像"输入没接上"，其实是"时间停了"。
    修法：结束判定必须区分两种模型 ——
    `const simDone = live ? battle.over : true;`，
    只有 `simDone && ui.frame >= totalFrames` 才算"这一局打完了"；
    播放键的"从头重看"同理（打一半时不能把播放头归 0，那和引擎状态对不上）。
    **教训：给一个模式加"实时"这种新时间语义时，把所有"用播放头位置表达状态"
    的判断都过一遍 —— 它们默认的假设（播放头 = 时间进度）已经不成立了。**

60. **"方向"有时候不存在弹道里，而是存在位置上** ——
    给所有弹道接上鼠标瞄准时，最简单的是在 `_spawnProjectile` 里
    "把速度旋转到鼠标方向"。但那会毁掉扇形：**每支箭都会被各自转到鼠标上**，
    五连发当场变成一支箭（五发重叠）。
    正确做法是在**技能算方向的那一处**替换成 `aimUnit()`：扇形基准转向鼠标、
    每支箭的相对偏移保持不变。
    同理，"只有位置没有弹道"的能力（棱镜光门、缇娜瞬移）根本不吃这套 ——
    它们的方向体现在**落点**上，得单独决定（本项目：光门跟着鼠标、
    瞬移仍朝最近的敌人）。
    **教训：加"全局改方向"这种能力时，先分清哪些效果的方向是弹道、
    哪些是位置、哪些是"每帧追踪"（追踪类不能改初始方向就完事）。**

61. **测试里手搓的鼠标事件坐标会覆盖掉刚移好的瞄准点** ——
    玩家操控的自检（`tests/diag/player.mjs`）里，
    `mousedown` 桩件一开始写死了 `clientX = 360`（画布中心）。
    而引擎在**按下那一刻也会用事件坐标更新瞄点** ——
    于是"把鼠标移到左边再开火"的用例量到的是"朝右飞"（中心在球的右边）。
    修法：桩件记住 `moveMouse` 的位置，按下时默认沿用。
    **教训：界面上"位置/状态"类的桩件不要写死常量 ——
    真实输入是连续的，写死就会把上一步的意图抹掉。**

62. **"每帧读一次按住状态"会把快速点按整发吞掉** ——
    作者报"手操有时特效不见了（如晕彩的魔弹）"。查下来最实的一条是这个：
    输入是**每帧现读一次** `keysDown`，而一次很快的点按如果
    **按下和松开都落在同一帧的间隙里**（16.7ms 内，卡顿时窗口更大），
    那一帧读到的就已经是"没按住"了 —— 这一发永远放不出去，
    表现就是"点了没反应"，而且时有时无。
    修法：维护 `keysDown`（按住）+ `keysEdge`（自上次喂给引擎以来按下过），
    技能键取两者之并，喂完清掉边沿。
    同一轮还顺手治了两个"看着像特效没了"的：
    · **技能栏盖住战场**：它原本是 `.stage` 里的绝对定位浮层，
      压在战场下沿 —— 球和弹道跑到那一条带里就被它挡住；
    · **实时模式没有预热弹道贴图**：全自动是"整局算完再预热"，所以贴图早就绪；
      实时操控在开战那一刻调 `preloadProjSprites` 时一枚弹都还没有，
      调色板是空的 —— 那种弹道要等第一次绘制才现加载，头一两帧只画程序化光点。
      现在每帧补一次（调色板/单位数一变就再预热）。
    **教训：凡是"每帧现读一次状态"的输入，都要想一遍"这个状态会不会在一帧之内
    从无到有再消失" —— 会的话就得锁存边沿。**

63. **加"开战要手动点一下"时，别拿"时间到了"当开始** ——
    闸门本身很简单（`ui.started` 为假就不推进），但有个细节：
    玩家可能盯着界面看十几秒才点开始，而循环里的 `dtms = now - ui.last`
    早就攒了一大截（夹到 120ms）—— 点下去那一帧就会"白跑" 7 帧，
    开局像被快进了一下。修法是点开始时置一个 `resetClock`，
    在下一帧把计时基准重置到当前 rAF 时间戳。
    **教训：任何"暂停了很久再继续"的地方，都要检查有没有一个隐式的
    "按墙上时钟补帧"在等着你。**

64. **"手操时特效依旧有可能消失" —— 贴脸开枪那一发，一帧都没被画出来** ——
    上一轮修了"快速点按被吞"和"贴图没预热"，作者复测后说**依旧**偶发。
    继续查下去，量到的是这个：玩家**贴着墙（或贴着敌人）开火**时，
    弹道在**出生的那一帧**就撞上东西 → `alive = false`；
    而快照是这一帧**末尾**才记的 —— 于是这一发**一张快照都没进过**，
    渲染层当然一帧都没画。玩家看到的就是"点了左键，屏幕上什么都没发生"。
    实测（临时探针的对照）：场地中间朝空旷处开火 → 进快照 **42 帧**；
    贴左墙朝墙外开火 → 进快照 **1 帧**（等于没画）。
    自动模式几乎测不出这个差别，因为 AI 永远朝敌人打 ——
    **它是个"只有玩家会踩"的坑**。
    修法：给弹道一条"最短可见时间"（`PROJ_MIN_VISIBLE_FRAMES = 5`）——
    出生头几帧不许直接消失，改成**冻在原地、把剩下的时间当寿命用来淡出**
    （渲染层本来就按 `life/maxLife` 做末端淡出，所以只改寿命就够）。
    冻住期间不再移动、也不再判命中与撞墙，因此**不会重复结算伤害、
    也不会多冒几次水花** —— 这两条都写进了断言。
    **教训：凡是"当帧出生、当帧就死"的对象，都要问一句
    "它到底以什么形式被画出来过" —— 快照是帧末记的，
    出生即死的对象在画面上等于不存在。**

65. **右键是技能键，而右键拖动是浏览器的"后退手势"** ——
    作者报"右键可能会唤起浏览器手势导致退出界面"。
    右键是默认的 2 号技能键（作者指定的），而按住右键拖动在不少浏览器 /
    鼠标驱动里是**后退手势**，一触发就跳走，这一局当场没了。
    修法两条：整个战斗界面屏蔽 `contextmenu` / `auxclick`
    （以前只挡了画布：在顶栏、侧栏、播放条上按右键照样弹菜单），
    再给路由挂一个"守门人"拦下非主动的跳转。
    两个细节值得记：
    · **"这一局还在进行"不能用 `battle.over` 判**：全自动模式是"开局就把整局算完"，
      `battle.over` 从一开始就是 true —— 守门人在那个模式下等于没挂
      （`check-boot` 直接把它抓出来了：模拟后退之后画布真的被换掉了）。
      判据要分模式：实时操控看引擎，全自动看播放头有没有播到头；
    · **换界面时必须 detach**：那些键盘/鼠标监听挂在 window 上，
      不摘掉的话回到准备界面后它们还在吞键盘事件（"按了没反应"的另一种来源）。
    **教训：给一个界面挂全局监听时，把"什么时候摘掉"写在同一处 ——
    挂上去容易，忘掉摘掉就是下一个幽灵 bug。**

## 木桩与测试球夹具

### 木桩（演示用靶子）

作者 2026-10 的要求：「新增一个木桩小球，速度恒定为 0，体型为大，
血量 5000，碰撞伤害 50，无技能，用于斗蛐蛐技能演示」。

| 项 | 值 | 说明 |
|---|---|---|
| `speed` | **0** | 永远不动 |
| `r` | **30** | 体型为大（直径 60，本体是 32） |
| `hp` | **5000** | 挨得住一整套技能演示 |
| `melee` | **50** | 碰上去才有伤害；它不会主动追人 |
| `skills` | `[]` | 无技能 |
| `immovable` | `true` | **推不动** —— 见下面为什么必须有这个开关 |

**为什么只写 `speed: 0` 不够**：`speed` 只决定"自己走多快"（巡敌、转向都按它给速度），
而碰撞冲量、分离推挤、击退、撞墙反弹这些都会**直接改 `vx/vy`** ——
木桩会被打得满地跑，那就没法当靶子了。所以引擎加了一个 `immovable`：

- `buildUnits` 里质量取一个极大的有限值（`1e9`，不是 `Infinity` ——
  两个木桩互相重叠时 `Infinity/Infinity` 会算出 `NaN` 把位置毁掉），
  `invMass ≈ 0` 于是碰撞冲量与分离推挤**全部转嫁给对方**，撞上来的一方自己弹开；
- 每帧积分之前再清一次速度，兜住那些绕开质量的通道（击退、冲刺、反弹、分离下限），
  所以"速度恒定为 0"没有例外；
- `_ensureMoving`（防止球停住的那个补丁）对木桩直接返回 —— 它静止是设计，不是卡住。

两处按设计存在的例外，都在 `tests/diag/dummy.mjs` 里钉着：

- **收缩竞技场**：边界往里收的时候引擎会把越界的球夹回场内，木桩被夹着挪了
  104 个世界单位（3394 帧里只有 13 帧变过位置）。那是"墙推它"，不是"它在走"——
  速度全程仍然是 0。
- **两个木桩对打永远打不完**：都动不了、碰不到对方，谁也伤不到谁。
  想收场就打开「比赛时长上限」（到点按剩余总血量判定）。这是"靶子"的必然结果，不是 bug。

### 测试球夹具（`tests/lib/test-balls.mjs`）

作者同时要求：「删去除了晕彩、缇娜、桃夭之外的所有测试用小球」。
但二十多个诊断脚本一直拿那几颗测试球当**参照物**：
`test`（1000 血 / 速度 120 / 碰撞 100）是纯物理断言的基准，
`test_skill`（定点射击 50 + 蓄力冲刺 200）用来验技能链路，
50 / 200 / 100 这几个数还被 `skill3.mjs` 写死当守卫。

直接删掉它们，这些脚本要么报错、要么**悄悄回落到默认球种**
（`makeUnitStats` 对认不出的 id 有兜底）—— 后者更糟：断言会"通过"，但测的已经不是它以为的东西。

所以做法是**把球种搬出游戏、搬进测试**：

```
js/balls.js               → 只有 4 个球：晕彩 / 桃夭 / 缇娜 / 木桩
tests/lib/test-balls.mjs  → 5 颗测试球（与当年逐字一致），import 即注册进 SPECIES
```

诊断脚本第一行都能看到 `import '../lib/test-balls.mjs';` ——
它们不再偷偷依赖游戏内容，而是**显式声明"我要用夹具球"**。
游戏侧一概看不到这几颗球：图鉴、准备界面、素材编辑器里都只有那 4 个。

> **为什么要保留"逐字一致"**：这些数就是所有断言的量纲（100 伤害、120 速度、1000 血）。
> 重新设计一套"更好"的测试球，等于把二十多个脚本的预期值全部重算一遍 —— 收益为零、风险极大。

## 技能测试球（诊断夹具，验证技能系统的样板）

> ⚠ 这两颗球**已经不在游戏里**了（见上一节），它们住在 `tests/lib/test-balls.mjs`。

`test_skill`（测试球·技能型）挂了两个技能，用来验证整条技能链路：

| 技能 | 触发 | 参数 | 表现 |
|---|---|---|---|
| `test_shot` 定点射击 | 冷却 2.5 秒 | 伤害 50 / 速度 300 / 半径 6 / 存活 3 秒 | 青色发光弹道（进快照，可暂停回放） |
| `test_dash` 蓄力冲刺 | 撞墙 | 蓄力 2 秒 → 冲刺最多 2 秒，初速 3×→1×，伤害 200，击退 270 | 蓄力进度环 + 冲刺光环 + 击退冲击线 |

> **冲刺时长是"上限"不是"定长"**：撞墙会立刻终止冲刺（然后由 `onWall` 接手进入蓄力）。
> 所以一次冲刺可能是 120 帧（自然跑完），也可能是 100 / 92 帧（撞墙提前结束）。
> 判据是"不超过 120 帧，且提前结束的每一段结尾都确实撞了墙"，
> 见 `tests/diag/skill.mjs` 与 `tests/diag/dash-wall.mjs`。

渲染层新增的东西（都来自快照，不碰引擎内部状态）：

- **弹道**：快照里存 `proj` 缓冲（步长 `PROJ_STRIDE`），颜色只存调色板下标；
  外发光 + 弹体 + 高光点。暂停会停在原地、回放会跟着倒回去。
- **蓄力进度环**：`SNAP_STRIDE` 里的 `mode / 蓄力进度 / 冲刺进度` 三个字段驱动。
  进度弧的扫角严格等于 `2π × chargeP`（测试里核对到 1e-16）。
- **事件特效**：`shoot`（枪口闪光）、`projHit`（爆点 + 星芒）、
  `projWall`（撞墙水花）、`dashStart`（起手炸环）、`knock`（推开冲击线）。

> 快照步长与弹道步长是 `core.js` 导出的 `SNAP_STRIDE` / `PROJ_STRIDE`。
> **所有读取快照的地方都要用这两个常数**，不要再写死数字 ——
> 改一个数字就等于改快照格式，写死的地方会静默错位。

| 工具 | 用途 |
|---|---|
| `serve.mjs` | 本地静态服务器（`node tools/serve.mjs` → 5173，被占用就顺延）。启动时打印**启动器 / 游戏 / 编辑器**三个地址；另带素材编辑器的写回接口 `POST /__edit`（只在**本机**监听、只认白名单字段）；`README.md` 按纯文本给，浏览器里能直接看 |

| `check-boot.mjs` | 「页面能不能开」自检（33 项）：真实 html + 入口模块跑一遍，游戏主页与素材编辑器页面都开、编辑器 24 个素材逐个点、数值（平衡）那几项的输入框逐个查空；首页→图鉴→准备→开战→战斗整条路由走一遍，并验证**开战闸门**（没点开始播放头不动）与**手势保护**（模拟后退被拦下、地址改回 #/battle、界面没被换掉、右键菜单被挡、自己点「重新准备」仍畅通） |
